# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Dungeon Architect — a top-down, tile-based roguelike editor/game built with pygame. Players will explore procedurally-composed dungeons and unlock tiles/monsters/traps/entities for a fully customizable, destructible home base between runs. See `DA.txt` (French) for the full design pitch and current priority list.

The grid uses 16x16px source art; each world grid cell renders that art at 2x, so a logical cell is 32x32px (see `core.data.ressources.WORLD_SCALE`). Single rooms are saved as JSON under `assets/rooms/`; procedurally-assembled multi-room dungeons under `assets/donjons/` (see Roadmap).

## Commands

- Run the app: `python main.py` (opens the main menu, `GameState.MENU`).
- Dependencies: `pygame==2.6.1`, declared in `requirements.txt`. **That file is UTF-16LE encoded** (not UTF-8) — `pip install -r requirements.txt` may fail to parse depending on pip version; if so just `pip install pygame==2.6.1` directly. A `.venv` already exists in the repo root.
- Headless smoke-test of the editor: set `DUNGEONARCHITECT_HEADLESS=1` before running — `GameManager` skips the menu and starts straight in `GameState.CREATOR`, and `Creator.run()` saves the current room and exits immediately instead of opening the pygame window/event loop.
- There is no test suite, linter, or build config in the repo.

## In-app controls

- Menu: `UP`/`DOWN` (or `Z`/`S`) to move the selection, `ENTER` or mouse click to confirm, `ESC` quits. Choosing "Editeur de salle" or "Explorer" opens a room-picker (see Architecture) before actually entering that state — "+ Nouvelle salle" (Creator only) starts a fresh untitled room.
- Editor (Creator): left-click an empty floor cell to paint, left-click-drag an already-placed object's body to move it, left-click-drag a linkable object's indicator dot (top-right corner of its tile — `button`/`gate`/`wall`) onto another one's dot to link them, drag object icons from the palette onto the grid to place new ones, right-click erase, mouse-wheel zoom, `TAB` switch to exploration, `ESC` back to menu (or, while previewing a generated dungeon, closes the preview first — see below). The Sauvegarder/Charger/Supprimer panel (top of screen) replaces the old F1-F4 console shortcuts entirely — "Charger" lists both rooms (`[Salle] name`) and saved dungeons (`[Donjon] name`) together. Below it (left column, under the tool/object palettes) is the generator panel: a room pool (checkbox-style multi-select, defaults to every saved room) and a room count (+/- stepper); "Generer" runs the procedural assembler, saves the result to `assets/donjons/`, and immediately shows it — while previewing, painting/object tools are suspended (they act on the normal single-room `Dungeon`, which isn't what's on screen).
- Exploration (Explorator): French AZERTY movement (`Z`/`Q`/`S`/`D`, not WASD), hold `SHIFT` to run (faster movement + `run` animation instead of `walk`), left-click to attack, right-click to interact, `SPACE` to jump (one-shot animations — see Roadmap), mouse-wheel zoom, `TAB` back to editor, `ESC` back to menu. Walking onto a linked `button` opens whatever `gate`/`wall` it's linked to.

## Architecture

`main.py` builds the pygame `screen` and hands it to `GameManager`, whose `run()` loop dispatches on `core.engine.gamestate.GameState` (`MENU` / `CREATOR` / `EXPLORATION`). Each state object owns **its own inner pygame event loop** (`Menu.run()`, `Creator.run()`, `Explorator.run()`) rather than there being one shared frame loop — switching state means setting `self.state` and breaking out of the current inner `while` loop, which returns control to `GameManager.run()` to dispatch into the next state's loop.

Package layout (`core/`):
- `engine/` — state machine plumbing: `GameManager` (also owns `pending_room`, set by `Menu`'s room-picker before switching to `CREATOR`/`EXPLORATION`; `run()` applies it via `creator.open_room()`/`explorator.open_room()` right before dispatching into that state's loop), `GameState`, `Camera` (world↔screen coordinate/zoom transform), `RoomManager` (thin wrapper around `Dungeon.save_to_json`/deleting a room file, plus `scan()`/`next_new_room_name()` — holds no "current room" state itself, that's each caller's concern; no console I/O, unlike its previous `input()`-driven incarnation), `input.py` (`InputState` — a per-frame input snapshot for one player, plus `read_local_keyboard_input(settings)`, a pure function fully separate from applying one; see the multiplayer-refactor Roadmap entry below).
- `editor/` — the room editor (`Creator`, the `CREATOR` state): `ui.py` has `ToolPaletteUI`, `ObjectPalette` (the draggable object-type icon tray, reuses `object_manager.load_object_frames`), `RoomPanelUI` (Sauvegarder/Charger/Supprimer buttons, each opening a `core.ui.widgets.RoomBrowser` + "Valider" button — `handle_event()` returns `(mode, selection)` once confirmed; for "load", `selection` is a `(kind, name)` tuple (`"room"` or `"donjon"`), since "Charger" lists both; for "save"/"delete" it's a plain room name), `GeneratorPanelUI` (a multi-select `RoomBrowser` for the room pool, a `core.ui.widgets.Stepper` for the room count, and a "Generer" button — `handle_event()` returns `(room_names, room_count)` once confirmed, letting `Creator` call `generate_assembly()`, save it, and preview it), `ChestPanelUI` (a `Stepper` per currency/item loot row for a placed chest); `tools.py` has `ObjectTool` (drag state for placing an object from the palette onto the grid); `autotile.py` is the tile-logic core (see below).
- `world/` — the dungeon data model: `dungeon.py` (`Dungeon` owns `width`/`height`/`logical_grid`/`sprite_grid` directly and orchestrates an `ObjectManager` + `WorldRenderer` + `SaveManager`; grid↔world coordinate conversion; `is_rect_walkable`/`update(dt)` delegate to `ObjectManager` — it draws nothing, saves nothing, and doesn't manage objects itself), `object_manager.py` (`ObjectManager(dungeon)` — takes the dungeon it belongs to; the `OBJECT_TYPES`/`OBJECT_LIST` registry of placeable object metadata — asset path, placement surface, footprint size in cells, frame count, and the gameplay flags `walkable`/`blocks_movement`/`blocks_until_open`/`linkable`; `get_object_at()` is footprint-aware (matches any cell a multi-cell object like `wall` covers, not just its origin); `is_cell_walkable()` is the single source of truth for whether a cell can be walked into, and `is_foreground_object()` the one for whether an object draws in front of / is walkable-despite-being-on-a-wall (currently: an L/R torch only, not the plain straight one); `check_button_trigger()`/`update(dt)` drive button→gate/wall activation and its frame-by-frame animation (holds on the last frame once reached — doesn't loop); `load_object_frames()` slices a sprite sheet, shared by the editor palette and the renderer), `assembly.py` (the procedural room-to-room assembler — see Roadmap), `entities.py` (`Player` — sprite-sheet animation keyed by direction, mirrors left-facing sprites from the right-facing frames, hitbox anchored at the feet; `Animal`/`AnimalManager` — the first live NPCs, see Roadmap; `Enemy`/`EnemyManager` — skeleton1/skeleton2, see Roadmap for aggro/attack behavior).
- `data/` — `ressources.py` (asset/tileset path resolution, tile metadata JSON loading, the `ROOMS_DIRECTORY`/`DONJONS_DIRECTORY` constants, `TILE_SIZE`/`WORLD_SCALE`, `list_rooms()`/`next_new_room_name()`/`list_donjons()`/`next_new_donjon_name()`), `save_manager.py` (`SaveManager` — stateless `save(dungeon, room_name)` / `load(dungeon, room_name)`, converts a `Dungeon` to/from its JSON room file; `apply_json(dungeon, payload)` factors out the payload-application half of `load()` so the assembly loader can reuse it per-room without a room-name-based file lookup).
- `rendering/` — `world_renderer.py` (`WorldRenderer.render(screen, dungeon, camera, spawn_preview=None, hide_object_types=None, show_link_indicators=False, skip_foreground_objects=False, hide_cells=None)`: draws the tile grid with a `(tile_index, zoom)` surface cache, placed objects sized from `OBJECT_TYPES[type]["size"]` (in grid cells, not raw sprite pixels) and at their current `obj["frame"]`, debug grid lines, the spawn-preview marker, and (only when `show_link_indicators=True`, which only `Creator` passes) each linkable object's indicator dot and any persisted links. `hide_cells` (a set of local (x, y)) skips specific cells entirely (tile and object) — used by `DungeonAssembly.render()` for the see-through hole. `render_foreground_objects()` draws only objects `ObjectManager.is_foreground_object()` flags — `Explorator` calls it after drawing the player so a foreground object (an L/R torch) overlaps the player instead of the other way around; `Creator` never calls it since it draws no player sprite, so it just renders everything in one `render()` pass. Holds no world state itself — only pygame surface caches).
- `ui/` — the state-agnostic shared UI layer, plus `Menu` (which is built almost entirely out of it and owns no world/simulation state of its own, unlike Creator/Explorator, so it lives here rather than in its own subpackage): `widgets.py` has `BorderManager` (the shared 9-slice panel renderer used by editor UI, `Menu`, and `InventoryPanel` alike — a singleton, first-initialized by whichever of those constructs it first), `RoomBrowser` (a scrollable/slider-scrollable selectable room-name list, with an optional `multi_select` mode (checkbox-style, toggles into `selected_set`) — purely a list-selector, callers decide what confirming a selection means; used by `Menu`'s room-picker, `RoomPanelUI`, and `GeneratorPanelUI`), `BorderPicker` (Settings > Bordure's clickable tile-sheet grid), `Stepper` (a "-  N  +" row — rects + min/max-clamped value changes on click; used by `editor/ui.py`'s `GeneratorPanelUI`/`ChestPanelUI`, previously each hand-rolled). `menu.py` has `Menu` (the `MENU` state: title screen with Editeur/Explorer/Parametres/Quitter, routes to `CREATOR`/`EXPLORATION` — but first through a room-picker mode reusing `RoomBrowser`, setting `game_manager.pending_room` and `.state` once "Valider" is clicked; `ESC` from either gameplay state now returns here instead of quitting — only the menu itself quits the program).
- `exploration/` — the `EXPLORATION` state, mirroring `editor/`'s "one game state = one subpackage, its own UI bundled alongside it" shape: `explorator.py` has `Explorator` (`self.players: dict[int, PlayerSession]` — see the multiplayer-refactor Roadmap entry below for why this replaced a single `self.player`/`self.inventory` — drives movement/collision/combat/camera-follow; `open_room(name)` loads a specific room and (re)spawns every current session's player in it, used both by the menu's room-picker and its own startup auto-discovery fallback `load_spawn_room()`; also has `run_networked(client)`, `apply_network_snapshot(payload)`, `add_network_session`/`remove_session`/`adopt_local_player_id` — the Phase 3 client/server entry points, see the Roadmap entry below); `player_session.py` has `PlayerSession` (bundles one player's `Player`, `Inventory`/`InventoryPanel`, per-frame `InputState`, and UI/audio state that's per-player, not per-world-session — `input_source_kind` includes `"network"` since Phase 3); `inventory_ui.py` has `InventoryPanel` (the "E" overlay, Explorator-only — not in `core/ui/widgets.py`, which is reserved for widgets actually shared across game states, same separation as `editor/ui.py` being Creator-only).
- `network/` — the multiplayer transport layer (Phase 3, `serv` branch only — see Roadmap): `protocol.py` (newline-delimited JSON message framing — `encode`/`encode_dict`/`decode` — plus `build_snapshot(explorator, tick, terrain_versions)`, the one place that knows the wire schema for a full world snapshot), `server.py` (`GameServer` — headless, owns one `Explorator`, fixed-tick loop), `client.py` (`NetworkClient` — thin socket-to-queue pump, no simulation).

Autotiling (`core/editor/autotile.py`), the core "logical grid" algorithm: cells are `EMPTY`/`FLOOR`/`WALL` ints. `build_walls()` does a two-pass pass over the grid — strip existing `WALL` cells back to `EMPTY`, then surround every `FLOOR` cell's empty neighbors (8-directional) with `WALL`. `resolve_sprite_grid()` then computes a 4-directional (`up`/`right`/`down`/`left`) neighbor bitmask string like `"0212"` per non-empty cell and looks up `(category, bitmask)` in `AUTOTILE_LOOKUP`, which is built at import time from `assets/tiles/tile_categories.json`, to pick the concrete sprite index.

## Roadmap

**Object placement rules — done:**
- `ObjectManager.add_object` now reads `OBJECT_TYPES[type]["placement"]` (`"floor"` or `"wall"`) instead of hardcoding `FLOOR` for every type — this also fixed a real bug where `torch` (wall-only) could never actually be placed. `gate`/`wall` use a third, custom placement (`"doorway"`, resolved by `ObjectManager.is_valid_doorway` rather than a plain lookup) — see the procedural-generation section below for why.
- `Dungeon.paint_cell` calls `object_manager.prune_invalid()` after every edit, which drops any placed object whose cell no longer matches its placement rule — so erasing a floor destroys the `gate`/`wall`/`button`/`vase`/`spawn` sitting on it, and erasing the floor that generated a wall segment destroys any `torch` mounted there too.
- `spawn` (and, since animal NPCs landed, every animal type too) is excluded from rendering during exploration: `WorldRenderer.render(..., hide_object_types=...)`, with `Explorator` passing its module-level `HIDDEN_OBJECT_TYPES` (`{"spawn", *ANIMAL_TYPES}`). `Creator` passes nothing, so both still show as their static placed-object icon in the editor.
- `torch` has variant-dependent placement (`ObjectManager._resolve_placement`/`_torch_variant`), not a single static rule: clicking a **floor** cell with a wall immediately beside it places an `L`/`R` variant (wall to the right → `R`, wall to the left → `L`); clicking a **wall** cell directly places the plain front-facing variant (no adjacent-floor requirement — this is the back-wall case). Stored as an optional `"variant"` key on the object dict (additive — old saves without it still load).

**Button/gate/wall linking — done, editor and runtime:**
- Any `button`/`gate`/`wall` (`OBJECT_TYPES[type]["linkable"]`) shows a small indicator dot at `Dungeon.object_indicator_position(obj)` (top-right corner of its cell) whenever `Creator` renders — `Explorator` never passes `show_link_indicators`, so links/indicators are invisible during exploration, per spec.
- Dragging from one indicator to another calls `ObjectManager.link()`, which records the connection symmetrically on both objects as an additive `"links"` list of `{"x", "y"}` targets (same additive-JSON-field approach as `torch`'s `"variant"` — old saves without it still load fine).
- `ObjectManager.move_object()` lets any placed object (not just linkable ones) be dragged to a new cell in `Creator` — it re-validates the placement rule at the destination, recomputes a torch's L/R variant if it moved, and retargets any other object's `links` that pointed at its old cell. `prune_invalid()` also drops links left dangling when the object they pointed at gets erased.
- At runtime: `Explorator.update()` calls `ObjectManager.check_button_trigger(grid_x, grid_y)` every frame using the player's hitbox (`hitbox.centerx`, `hitbox.bottom - 1` — not raw `player.position`, which sits exactly on the cell's bottom boundary and would floor-divide into the row below). Stepping onto an unactivated `button` sets `obj["activated"] = True` and opens (`obj["open"] = True`) every `gate`/`wall` it's linked to; it's a one-shot latch, not a toggle. `ObjectManager.update(dt)` (called from `Dungeon.update`, which `Explorator` calls every frame) advances `obj["frame"]` for any activated/open object at a fixed rate and **holds on the last frame** once reached rather than looping.
- Walkability is `ObjectManager.is_cell_walkable(x, y)`, not a raw `logical_grid` check: `button` is always walkable; an L/R `torch` is walkable because it sits on a floor cell to begin with (see placement above) and is drawn in front of the player there (`ObjectManager.is_foreground_object`) instead of behind; the plain straight torch (placed directly on a wall cell) stays a normal blocking wall decoration. `gate`/`wall` block until their `"open"` flag is set. `vase` always blocks (`"blocks_movement"`). `Dungeon.is_rect_walkable` (used for player-movement collision) delegates to `is_cell_walkable` per hitbox corner instead of checking `WALL` directly.
- `get_object_at(x, y)` is footprint-aware: it matches any cell within `OBJECT_TYPES[type]["size"]` of an object's origin, not just the origin itself. This is what makes a 2-wide `wall` object correctly block (and later open) *both* of its cells, not just the one it was placed on — it also means clicking the second cell of a wide object in `Creator` lets you grab it to move, same as clicking its origin cell. `WorldRenderer` positions a multi-cell object's sprite anchored to its footprint's left/bottom edge, not centered on the origin cell — centering a sprite wider than one cell on that cell's center would make it visually bleed half a tile into the neighbor on each side, out of alignment with what `get_object_at` actually considers blocked.
- These are all additive object-dict fields (`activated`, `open`, `frame`, `anim_timer`), so a saved room can reload with its buttons/gates already mid- or fully-triggered.

**Procedural room-to-room generation — data model, algorithm, persistence, rendering, Creator preview, and live Explorator traversal all done:**
- **A `gate`/`wall` entry-exit must sit on a real wall-doorway cell**, enforced by `ObjectManager.is_valid_doorway(x, y)`: the cell itself must be WALL, with exactly one FLOOR neighbor (the room interior) directly opposite exactly one EMPTY neighbor (the void beyond) and WALL flanking the other two sides — the shape of a clean break in a straight wall segment. This replaced an earlier, too-permissive rule (any FLOOR cell, same as `button`/`vase`) that let an E/S be dropped in the middle of a room, indistinguishable from an ordinary floor tile — which is exactly what made it ambiguous, mid-crossing, whether a given cell was "just floor" or a doorway to another room. `ObjectManager.add_object`/`move_object` both go through this check for `gate`/`wall`, and `core.world.assembly._valid_entry_exits(dungeon)` re-applies the identical check when the procedural assembler collects a room's usable connectors (shared by `PlacedRoom.entry_exits`, `_find_start_room`, and candidate selection in `generate_assembly`) — a `gate`/`wall` with no void neighbor (e.g. a locked door gating a windowless side room, never meant to connect elsewhere) simply isn't picked as a room-to-room connector; it still works as an ordinary in-room obstacle. **Consequence:** rooms saved under the old rule (gate/wall anywhere on FLOOR) now have zero valid entry-exits until their gate/wall objects are dragged onto a proper wall cell in the editor — `move_object` re-validates through the same check, so the palette of valid cells is discoverable by just trying to drop it somewhere.
- `core/world/assembly.py`: `PlacedRoom` wraps a `Dungeon` with a floor index and a global grid offset. `generate_assembly(room_names, room_count)` starts from the first room (in `room_names` order) with both a `spawn` and a valid `gate`/`wall` entry-exit, then repeatedly draws another room at random from `room_names` (repeats allowed) and attaches it at one of the growing assembly's unconnected entry-exits — aligned so the two entry-exit objects share the same global cell. The candidate's exit is only ever chosen from objects matching the anchor exit's own type (a `gate` merges with a `gate`, a `wall` with a `wall`, never mixed) so both halves of one physical doorway share the same sprite/animation. If the new room's tiles would conflict with an already-placed room on the same floor (anything except two rooms' auto-generated wall halos meeting, or the entry-exit cell itself — both expected, not conflicts), it goes on floor +1 instead (or -1 if that's also occupied), always relative to the floor of the room it's connecting from.
- Cross-room link inheritance: rather than copying the anchor exit's local `links` verbatim (meaningless once the two ends live in different rooms' object lists), `generate_assembly` finds any `button` in the anchor room whose `links` reference the anchor exit and appends a global, floor-qualified `assembly_links` entry (`{"floor", "x", "y"}`) pointing at the candidate's merged door.
- `save_assembly(assembly, name)`/`load_assembly(name)` persist to `assets/donjons/<name>.json` as one combined file: each room is stored fully (`SaveManager.to_json()` per room, plus its floor/offset) rather than just a reference to its source room file, since generation mutates objects (link inheritance, `portal_level` below) that a fresh reload from `assets/rooms/` would lose. `Creator._apply_generation` calls `save_assembly` right after generating (via `next_new_donjon_name()`), and `RoomPanelUI`'s "Charger" lists donjons alongside rooms so a saved one can be reloaded.
- `Creator.open_donjon(name)` loads a saved assembly and `Creator.run()` renders it (`DungeonAssembly.render`, `active_floor=0`) in place of the normal single-room edit view whenever `self.last_assembly` is set — painting/object tools are suspended while previewing (they act on `self.dungeon`, not what's on screen); `ESC` closes the preview before it falls through to the menu.
- **Collision is scoped to the player's current floor, on purpose.** Two `PlacedRoom`s on different floors routinely share a bounding box (they're often the same source room reused), so `DungeonAssembly.locate_room(global_x, global_y, floor, prefer_room=None)` only ever searches `rooms_on_floor(floor)` — never other floors — checking FLOOR ownership first and falling back to "any non-empty cell" (a WALL halo) only if nothing on that floor claims FLOOR there. Searching every floor at once (the original design) let the player "phase" through a wall solid on their own floor whenever an unrelated room on another floor happened to have FLOOR at that same global cell. `is_global_cell_walkable`/`is_rect_walkable`/`check_button_trigger` all take the same explicit `floor` and mirror the single-`Dungeon` equivalents through it.
- **Crossing floors is an explicit, data-driven portal, not a side effect of collision.** Whenever a connection actually lands on a different floor, `generate_assembly` stamps a `"portal_level"` field directly onto *both* halves of the doorway (the anchor's exit object and the candidate's exit object) — the half-integer midpoint between the two floors it bridges (e.g. `0.5` between floors 0 and 1, `1.5` between 1 and 2), the same value on both sides since it's the same physical staircase either way. It's additive, just like `variant`/`links`/`open` — no separate room-level list, so it round-trips through `SaveManager`'s already-generic `objects` list for free. `DungeonAssembly.find_portal(room, global_x, global_y)` reads the object at that cell and derives the actual target floor relative to whichever side you're asking from: `target = 2 * portal_level - room.floor`. Reaching a portal cell at all already implies the current floor's own collision allowed it (e.g. a button-opened gate), so no separate "is it open" check is needed before crossing. Same-floor attachments don't get a `portal_level` — ordinary same-floor room-crossing already works via `locate_room`.
- `Explorator._update_current_room()` resolves same-floor room-crossing via `locate_room`, then checks `find_portal` on the result to flip `self.current_placed_room` (and therefore floor) when the player steps onto a portal cell. `_is_walkable`/button-triggering pass `self.current_placed_room.floor` explicitly into the assembly API above.
- **Rendering** (`DungeonAssembly.render(screen, camera, active_floor, player_world_pos=None, ...)`): the active floor draws directly onto `screen`; floors below are drawn onto an offscreen per-pixel-alpha surface and alpha-multiplied down to `BELOW_FLOOR_ALPHA` (45/255, a faint tint) before compositing; floors above are alpha-multiplied to `ABOVE_FLOOR_ALPHA` (235/255, a near-opaque "ceiling") and then punched with a circular hole (`BLEND_RGBA_MULT` against a mask surface) of radius `VISION_RADIUS_TILES` (2.5 tiles, in screen pixels scaled by `camera.zoom`) centered on `player_world_pos` — a continuous pixel position, not a grid cell — so the ceiling fades away exactly where the player's field of view reaches it, revealing the active floor underneath. `player_world_pos=None` (Creator's static preview, which has no player) renders floors above fully opaque. `skip_active_floor_foreground` + `render_active_floor_foreground()` let a caller that draws its own player sprite (`Explorator`) interleave the player between the active floor's tiles and its foreground objects (e.g. an L/R torch), same z-order as the single-room case. This superseded the old single-hidden-grid-cell approach, so `hide_cells` was removed from `WorldRenderer`/`Dungeon.render()` entirely (no other callers).
- `Menu`'s Explorer picker lists donjons alongside rooms (mirroring `RoomPanelUI`'s `(kind, name)` tuple pattern) via `GameManager.pending_room`.

**First non-player entities: wandering animal NPCs — done, editor placement and live Explorator behavior:**
- Four animal object types (`chicken`, `cow`, `pig`, `sheep`) were added to `OBJECT_TYPES`/`OBJECT_LIST`, each backed by `assets/characters/Animals/<Name>.png` — a 64x64 sheet, 2x2 grid of 32px frames (row 0 idle, row 1 move) — flagged `"animal": True`, from which `object_manager.ANIMAL_TYPES` is derived (`tuple(name for name, cfg in OBJECT_TYPES.items() if cfg.get("animal"))`) instead of a separately-maintained list. They use the plain `"floor"` placement rule, same as `vase`, so they drop/drag/save through the exact same `ObjectPalette`/`ObjectTool`/`ObjectManager.add_object`/`SaveManager` path as every other object — no new plumbing was needed there.
- `ObjectPalette` (`core/editor/ui.py`) used to lay its icons out in a single row sized for the original 6 object types; with 10 now, `load_icons()` wraps into a `COLUMNS = 5` grid and computes `self.height` from the resulting row count, and `Creator` positions `GeneratorPanelUI` below it (`y=object_palette.y + object_palette.height + 20`) instead of a hardcoded offset, so the two panels never overlap regardless of how many object types exist.
- `load_object_frames()` (the static-icon loader shared by the palette and `WorldRenderer`) grew a `config.get("frame_size", ...)` lookup instead of a hardcoded 16px (24px for `spawn`) — an animal's `"frame_size": 32` combined with its `"frames": 2` means it reads exactly the idle row, so a placed animal shows as a static idle-frame icon in both the palette and the editor grid, identical in spirit to how `vase`/`torch` render.
- **Live behavior is a separate loader and a separate entity, deliberately not folded into `ObjectManager`.** `load_animal_frames()` (`object_manager.py`) reads the *full* 2x2 sheet into `{"idle": [...], "move": [...]}`, and `core.world.entities.Animal` — a new class alongside `Player` — owns per-frame wandering behavior: a random timer alternates `idle`/`move`, entering `move` picks a random direction (any angle, not just 4-directional) and a random duration, and position updates are collision-checked per-axis exactly like `Player.update` (movement on an axis is simply skipped if the resulting hitbox isn't walkable — no bounce/redirect). `AnimalManager` (also in `entities.py`) owns the *list* of live `Animal`s for one `Dungeon`, spawned from its placed animal objects via `spawn()` — mirroring `ObjectManager`'s "dungeon-owned component" shape, but for per-frame NPC behavior instead of static placement rules, and kept as its own list rather than mixed into `ObjectManager.objects` so a wandering `Animal`'s live position never gets confused with its origin object's fixed grid cell (the placed object itself never moves — that's what actually round-trips through `room.json`).
- `Dungeon` owns an `AnimalManager` (`self.animal_manager`) alongside its existing `ObjectManager`/`WorldRenderer`/`SaveManager`, and `Dungeon.update(dt, player_hitbox=None)` now advances it too (`object_manager.update(dt)` + `animal_manager.update(dt, player_hitbox=...)`). `Dungeon.render()` draws `self.animal_manager` after the normal tile/object pass (no y-sorting against the player — out of scope for this first pass). **Spawning is opt-in, not automatic**, via `Dungeon.spawn_animals()`: it's *not* called from `rebuild()`/`paint_cell()` (which would reset every animal's wandering state on every single paint stroke) and *not* called by `Creator` at all (whose static preview only ever wants the frame-0 icon, matching every other object type) — only `Explorator` calls it, right after loading a room (`open_room`, `load_spawn_room`) or each room of a loaded assembly (`open_donjon`). Because `DungeonAssembly.update(dt, player_hitbox=None, player_floor=None)` was changed to call `room.dungeon.update(dt, player_hitbox=...)` (previously it called `room.dungeon.object_manager.update(dt)` directly, and passed no player info at all), and rendering already threads every room's own `Dungeon.render()` through an `_OffsetCamera` per floor (`_render_floor`/`_render_floor_tinted`/`_render_floor_masked`), animals in a procedurally-assembled dungeon get the exact same per-floor update/tint/mask treatment as tiles and objects for free — no assembly-specific animal code was needed. `player_hitbox` is only ever forwarded to the room on `player_floor`; every other room gets `None`, so an animal on a floor the player isn't physically standing on never collides with them (mirrors `locate_room`'s per-floor scoping).
- `Explorator`'s module-level `HIDDEN_OBJECT_TYPES = {"spawn", *ANIMAL_TYPES}` replaces the old `{"spawn"}` literal at all four of its `hide_object_types=` render call sites, so a placed animal's static object icon never double-renders alongside its live `Animal` sprite during exploration.

**Animal collision/animation polish — done:**
- **Fixed a real 1px wall-clip bug** (reproduced with a 20000-frame stress test: an animal's hitbox ended up overlapping a WALL cell in ~15% of frames before the fix, 0 after). Root cause: the original `Animal.update` mutated a `pygame.Rect` in place (`hitbox.x += movement.x`) to build the candidate hitbox it tested, then applied the raw float `movement.x` straight to `self.position.x` on success — but assigning a float to a `Rect` field *rounds*, while `get_hitbox()` (called fresh every other frame) *truncates* (`int(...)`) from the live float position. Those two roundings of the same quantity can disagree by a pixel, so a move could validate against a rect that was up to 1px more conservative than the hitbox the animal actually settled into. Fixed by adding `Animal._hitbox_at(x, y)` — the one formula both `get_hitbox()` and collision-testing now share — and testing candidate positions by computing `self._hitbox_at(candidate_x, self.position.y)` directly from the prospective float position instead of mutating an existing Rect, so the tested hitbox and the one the animal actually ends up with are always identical.
- **Animal-vs-animal and animal-vs-player collision**, previously nonexistent (animals and the player could freely overlap). `AnimalManager._is_free(rect, moving_animal, player_hitbox)` checks, in order: `Dungeon.is_rect_walkable` (walls/closed gates, cheapest/most likely to reject), every *other* live animal's current hitbox via `rect.colliderect(...)`, then the player's hitbox if supplied. This is the `is_walkable` callback `AnimalManager.update` now hands each `Animal.update` (one small lambda closure per animal per frame, capturing that animal so it never collides with itself). Symmetrically, `Explorator._is_walkable` (used for the player's own movement) was extended to also reject any candidate rect overlapping a live animal in the player's current room, so the player can't walk through an animal either — both directions use plain `Rect.colliderect`, i.e. exact pixel-rect overlap, not a coarser cell-level check.
- **Animation flip direction fixed**: the animal sheets face left by default (opposite of `Player`'s sheets, which face right), so `Animal._enter_state("move")` now sets `self.flip = self.direction.x > 0` (flip when heading right) instead of the original `direction.x < 0` (which had it backwards — an animal walking right displayed its left-facing idle/move frames un-flipped).

**Assembly-mode collision offset fix, and Y-sorted entity rendering — done:**
- **Real bug: animal-vs-player collision compared local and global coordinates directly in a multi-room assembly.** An `Animal`'s `.position` (and therefore `get_hitbox()`) is always local to its own room's `Dungeon` — it's built via that room's own `grid_to_world`, with no `PlacedRoom.offset_x`/`offset_y` baked in (the offset only ever gets applied at render time, via `_OffsetCamera`). The player's hitbox, by contrast, is global (`Explorator`/`Player.position` always carry the room offset already summed in). `DungeonAssembly.update` was handing that global `player_hitbox` straight to each room's `AnimalManager` unmodified, so for any room not sitting at offset `(0, 0)` the animal-vs-player overlap check was comparing two rects in different coordinate spaces — reproduced with a large-offset stress test (offset 100 tiles: the "block" never registered at all). Fixed by having `DungeonAssembly.update` shift `player_hitbox` back into each room's local frame (`player_hitbox.move(-room.offset_x * tile_size, -room.offset_y * tile_size)`) before passing it down, mirroring how `is_global_cell_walkable` already converts global to local before delegating to a room's own `ObjectManager`. Animal-vs-animal collision was never affected (both sides always compared within the same room's local coordinates already).
- **Y-sorted rendering of live entities** (player + animals): previously `Dungeon.render()` always drew every animal in one unconditional pass *before* `Explorator` drew the player afterward, so the player was always in front regardless of actual on-screen depth. `Dungeon.render(..., skip_animals=False)` and `DungeonAssembly.render(..., skip_active_floor_animals=False)` (which threads it through `_render_floor`) let a caller opt the *active* floor's animals out of that automatic pass; floors below/tinted and above/masked always draw their animals normally (no player there to sort against, and they're dimmed background regardless). `Explorator.render()` now does its own combined pass afterward: single-room branch sorts `dungeon.animal_manager.animals + [player]` by `.position.y` (their shared feet-anchor, the same quantity `get_hitbox()` anchors to) and draws in that order, so whichever entity sits lower on screen (greater y, closer to camera in a top-down view) draws in front; the assembly branch does the same via the new `DungeonAssembly.render_active_floor_entities(screen, camera, active_floor, player)`, gathering animals across every room on the active floor (converting each to a comparable global y — `animal.position.y + room.offset_y * tile_size` — purely for the sort key; actual drawing still goes through that room's own `_OffsetCamera`) plus the player, in one sorted pass. Both call sites replace what used to be a bare `player.draw(...)` call, now sandwiched between `render(..., skip_..._animals=True)` and the existing foreground-object pass (`render_foreground`/`render_active_floor_foreground`), so the z-order is: floor tiles/objects → sorted animals+player → foreground objects (L/R torches), same slot the player alone used to occupy.

**Player: remaining action animations and inputs — done:**
- Four more animation sheets were already listed in `Player.ANIMATIONS` (`attack`, `interact`, `jump`, `run`) and `Player.cut_sheet()` already derived each row's frame count from that specific sheet's own pixel width (`columns = sheet.get_width() // FRAME_WIDTH`), not a hardcoded constant — so no loader changes were needed to support `attack.png` (6 frames/row), `interact.png` (4), `jump.png` (5), and `run.png` (6) each having a different frame count. `jump.png` is also short a row (110px tall = 4 rows, not the full 5 `DIRECTIONS` — it has no `"back"` frames), which `cut_sheet`'s existing `if row >= len(DIRECTIONS): break` guard tolerated for *loading*, but `update()`/`draw()` still indexed `self.sprites[animation][direction]` directly and would `KeyError` the moment the player faced `"back"` while jumping. Fixed with `Player._frames_for(animation, direction)`, now used by both, which falls back to `"front"` and then to whatever direction the sheet *does* have.
- **One-shot action animations**: `attack`/`interact`/`jump` (`Player.ONE_SHOT_ANIMATIONS`) play through once and hand control back, unlike the looping `idle`/`walk`/`run`. `Player.play_action(name)` starts one (no-op if another action is already mid-playback, or if that sheet failed to load) by setting `self.action = name` alongside `self.animation`; `Player.update()` clears `self.action` back to `None` the moment that animation's frame counter would otherwise wrap past its last frame, instead of looping it. `Explorator` only assigns `self.player.animation = "run"/"walk"/"idle"` from movement state when `self.player.action is None`, so a triggered action animation isn't stomped by the very next frame's movement-driven assignment, and resumes normally once the action completes.
- **Inputs**: `Explorator.run()`'s event loop now also handles `MOUSEBUTTONDOWN` (button 1 → `play_action("attack")`, button 3 → `play_action("interact")`) and `KEYDOWN` `K_SPACE` (→ `play_action("jump")`) — one-shot triggers, unlike movement's continuous `pygame.key.get_pressed()` polling. `SHIFT` (either key) is polled every frame in `Explorator.update()` alongside `Z`/`Q`/`S`/`D`: holding it while moving swaps `MOVE_SPEED` (180px/s) for the new `RUN_SPEED` (260px/s) and picks the `"run"` animation over `"walk"`.

**Post-Phase-2 polish pass (before starting Phase 3) — done:**

A void cell is real, walkable-into terrain (see `Explorator._is_void`/`_attempt_fall`), not a gap to visually patch over, so this is now purely a debug visualization of the logical grid's floor boundary, exactly like the grey `show_grid` grid lines it's now gated alongside.

Now also checks `_visible_animals_global()` and calls `animal.take_damage(1)` on hit -- no `_spawn_loot` call for animals, since they have no loot table (`OBJECT_TYPES`'s animal entries define no `"loot"` key, unlike `ENEMY_STATS`).
- **The void mechanic (falling into/being destroyed by empty terrain) now applies to every live entity, not just the player.** New `Dungeon.is_void_at(grid_x, grid_y)` (out-of-bounds or an `EMPTY` logical cell) is shared by `Explorator._is_void_at`'s single-room branch (deduped, was a local copy of the same check) and by a new module-level `_is_over_void(dungeon, entity)` in `entities.py` (see the pre-Phase-3 refactor pass below for why it's one function, not two), used by `AnimalManager`/`EnemyManager`'s and `PickupManager`'s own per-frame void-culling. None of this required touching `AnimalManager`/`EnemyManager`/`PickupManager`'s movement/`is_walkable` logic -- `ObjectManager.is_cell_walkable` already treated `EMPTY` as walkable (`!= WALL`), so entities could already wander onto void; only the "then what" consequence was missing.
- **PvP (players damaging each other) is now a togglable debug mode, off by default** -- `Explorator.pvp_enabled`, toggled by `F4` (deliberately separate from `F3`'s `debug_mode`, so PvP can be on/off independently of whether the debug overlay is showing). Player-vs-player *collision* (Phase 2) is unaffected and stays always-on/non-optional, per explicit instruction -- only combat damage is gated. `_resolve_player_attacks`, when `pvp_enabled` is `True`, additionally checks every *other* session's hitbox against the attacking player's `attack_hitbox` and calls `take_damage(1)` on a hit, mirroring how an enemy already damages a player.

**Multiplayer refactor, Phase 3 — couche transport (headless authoritative server + thin network clients, JSON-over-TCP) — done:**
- **Thin client, no prediction** (confirmed with the user before starting): the client never simulates the shared world locally. It sends its own input to the server every frame and renders exactly what the server's snapshots say, including its own player's position — so movement has one full round-trip of latency before it's visible. Fine on LAN; client-side prediction/reconciliation is an explicit later phase, not attempted here.
- **The server reuses `Explorator` almost entirely, not a parallel simulation.** `core/network/server.py`'s `GameServer` constructs a screen-less `Explorator` (`_HeadlessGameManager`, the minimal `screen`/`settings`/`state`/`running` surface `Explorator.__init__`/`_game_over` actually touch — no real `GameManager`, no `Menu`/`Creator`), clears the local id-0 session `__init__` always creates (a server has zero local devices — every session arrives over the network), loads exactly one room/donjon (`--room`/`--donjon`, mutually exclusive, required), then runs its own `time.sleep`-paced fixed-tick loop (`TICK_RATE = 30`) calling `explorator.update(dt)` **completely unchanged** every tick and never calling `render()`. This reuses 100% of movement/collision/combat/pickups/buttons/void/camera-math logic with zero forking.
- **One small, surgical `Explorator` change made this possible**: `_read_input()` gained a `"network"` branch (`PlayerSession.input_source_kind`) that reads `session.network_input` (written by the server's own connection-reader thread, `None` until the first message arrives) instead of polling a local device — everything downstream (`session.pending_actions` merging, `_apply_requested_actions`, `_simulate_movement`) needed no changes at all, since they already only look at `session.input`, never at where it came from. New `Explorator.add_network_session(player_id)`/`remove_session(player_id)` (server-side: create/spawn or drop a `PlayerSession` when a client joins/disconnects, mirroring `open_room`'s own per-session spawn loop) and `apply_network_snapshot(payload)`/`adopt_local_player_id(new_id)` (client-side, see below).
- **Real bug this surfaced, fixed in `_camera_frame()`**: it unconditionally indexed `positions[0]`, which every local mode always had (there's always at least one local player) but a server has zero players until the first client connects — the very first `update()` tick on an empty server crashed. Now returns a sentinel `(0.0, 0.0, self.camera.zoom)` when `self.players` is empty; harmless since a server never renders (the camera frame is otherwise unused there).
- **The client also builds on `Explorator`, driven by a new `run_networked(client)`** instead of `run()`: same event handling for QUIT/mouse-wheel-zoom/F3/ESC (TAB has nothing to switch to on a network client, ignored), but **F4 sends a `pvp_toggle` request instead of flipping `pvp_enabled` locally** — it gates real damage, so it must stay server-authoritative like every other simulation fact. Each frame: `_read_input()` (reused as-is — the client's one real local session is `"keyboard"`/`"gamepad"`, any mirrored remote sessions are harmlessly `"network"` with `network_input=None`, producing an idle `InputState()` nobody uses) → send that `InputState` to the server → drain incoming `snapshot` messages (each fully replaces the previous, no queue buildup) → `apply_network_snapshot` → `_update_camera()` (now doing double duty as the zoom-to-fit across every connected player, same math as local co-op) → `render()`. **`render()`/`WorldRenderer`/`Player.draw`/`Animal.draw`/the debug overlay/the inventory panel needed zero changes** — they already only read state off `Player`/`Animal`/`Enemy`/`Dungeon` objects, which now happen to be snapshot-driven instead of simulated.
- **`apply_network_snapshot(payload)`** writes every field straight onto the client's local mirror world, no physics recomputed: per-session `Player` fields (position/direction/animation/action/frame/health, creating a mirror `PlayerSession` the first time an id is seen, pruning any that vanish from the snapshot); a generic `_sync_mirror_list(mirror_map, live_list, entries, factory, updater)` reconciles each dungeon's `animal_manager.animals`/`enemy_manager.enemies`/`pickup_manager.pickups`/`item_pickups`/`projectile_manager.dynamites`/`explosions` against that tick's entries the same way (create-on-first-sight via a bare `factory(entry)` instance, update every tick, drop on disappearance) — `mirror_map` persists across ticks on `self._network_mirrors` (`{room_ref: {category: {network_id: local_object}}}`, lazily created, client-only). Every object's `activated`/`open`/`frame` flags are patched by list index (stable since client/server load the identical room JSON and nothing adds/removes objects during exploration). **Terrain destruction** (`Dungeon.destroy_area`) isn't diffed — the server tracks each room's `terrain_version` (`{room_ref: last_sent_version}`) and includes that room's full `logical_grid`/`sprite_grid` in a tick's snapshot only when the version has advanced since the last one sent; the client just assigns them directly. Simpler than shipping `(grid_x, grid_y, radius)` and replaying `destroy_area` client-side, and destruction is rare enough that shipping the whole grid on the rare tick it happens is cheap.
- **Room/entity identity across the wire**: a room is `None` (single-room mode) or a `PlacedRoom.index` (assembly mode) — the snapshot covers *every* room in the assembly, not just the active floor, since `Explorator.render` already draws floors below/above tinted and their live state matters too (small-dungeon assumption, see below). A live entity's network id is just Python's own `id()` of the server-side object for that process's lifetime — never persisted, never meaningful across a reconnect, purely an opaque per-tick dict key the client uses to track add/update/remove.
- **Wire protocol** (`core/network/protocol.py`): newline-delimited JSON, one `json.dumps(...) + "\n"` per message, binary-mode sockets throughout (`decode()` accepts `str` or `bytes`). Client→server: `join` (name, sent once), `input` (an `InputState`'s fields every frame), `pvp_toggle`. Server→client: `welcome` (assigned `player_id` + which room/donjon to open locally), `snapshot` (`build_snapshot`'s full-state dict, every tick), `leave` (a session disconnected — client-side pruning also happens naturally via the next snapshot's absence, so this is closer to a courtesy/log signal than something the client strictly needs).
- **`main.py` gained `argparse`** with three mutually exclusive modes, all opt-in — plain `python main.py` (no flags) is byte-for-byte today's local game: `--server --port N (--room NAME | --donjon NAME)` (headless, `GameServer.serve_forever()`, never touches `GameManager`) and `--connect HOST:PORT [--name X]` (normal `pygame`/`GameManager` construction, but blocks briefly on `NetworkClient.wait_for_welcome()`, calls `open_room`/`open_donjon` + `adopt_local_player_id` from that payload, then drives via `run_networked` instead of `GameManager.run()`).
- **Threading model** (`GameServer`): one accept thread; one reader thread per connected client (blocking `readline()` → decode → push onto a shared `queue.Queue`); the single main thread is the only thing that ever calls `Explorator.update()` or writes a broadcast, so there's no locking around the simulation or the write path itself — only `self._clients` (mutated by connection threads, read by broadcast) is guarded. `NetworkClient` mirrors this with one reader thread pushing onto its own queue, drained once per client frame.
- **Real bug found and fixed during verification**: `NetworkClient.close()` originally just called `self.sock.close()` — but `socket.makefile()`'s returned file objects each hold their own reference to the underlying fd, so the plain `close()` never actually tore down the TCP connection while `self._reader_file`/`_writer_file` were still alive, meaning the server's blocking `readline()` never saw EOF and never pruned the disconnected session. Fixed by calling `self.sock.shutdown(socket.SHUT_RDWR)` first (acts on the real OS socket immediately, independent of how many Python-level file-object references remain) before closing everything. Caught by a real two-process localhost smoke test (`GameServer` in a background thread + two real `NetworkClient`/socket connections) asserting a disconnected player actually gets pruned from the surviving client's mirror — not just asserted from reading the code.
- **Explicit, flagged simplifications** (not silently decided): no client-side prediction/reconciliation (see above); full-state snapshot every tick, no delta compression (simplest correct thing for 2-4 players in a small dungeon — revisit only if bandwidth actually becomes a problem); no reconnection (a dropped connection frees that `player_id` permanently — rejoining is a fresh `join` and a new id); no auth/encryption (trusted LAN/local-network scope, matching "small co-op among friends"); victory/game-over stays whole-session, unchanged from Phase 2's own policy, now surfaced to clients via the snapshot's `victory`/`game_over` fields (the server stops ticking and its process ends on game-over — there's no server-side Menu to fall back to); a Phase 1/2 local-co-op second session (gamepad/second-keyboard) sharing the same machine as a network client is not combined with network play — if a gamepad happens to be connected, `Explorator.__init__` auto-creates that local session same as always, but it's silently pruned by the very first snapshot (never in `seen_players`, and never `_local_player_id`), so at most a one-frame visual artifact, never a real bug.
- Not yet done, per the original roadmap: client-side prediction/reconciliation (Phase 4, done — see below) and server authority hardening (Phase 5, done — see below) are complete. **Phase 6 was expanded and split at the user's request** (see "Multiplayer refactor, Phase 6a" below) into a full first-launch/home/progression system — 6a (tileset/object foundations), 6b (progression), 6c (real split-screen), 6c-original (home room + zoom-driven Explo/Creator switch), and 6e (in-game host/join over LAN + chat/commands + the dungeon-entry sync barrier — this is where the original "lobby/identity/reconnection" idea resurfaces — see "Phase 6e (partial)" and "Phase 6e (continued)" below) are all done. Phase 7 (delta-compressed snapshots) is next.

**Multiplayer refactor, Phase 4 — client-side prediction + reconciliation, plus remote-entity smoothing — done:**
- **Scope, confirmed with the user before starting**: prediction covers the local player's *movement* only (position/direction/collision/walk-run animation) — `attack`/`interact`/`jump` stay purely server-authoritative, same as Phase 3 (the client only starts showing one once the snapshot reflects it). Falling into the void, death, and room/floor transitions are also not predicted — the snapshot decides those unconditionally, the client just follows once it arrives. Reconciliation corrections are a hard snap-and-replay, not smoothed separately (see below, this is inherently invisible in the common case). Remote-entity smoothing (other players, animals, enemies, pickups, projectiles) was folded into this same phase at the user's request, since it addresses the same underlying "30Hz server tick vs 60fps client render" visual gap.
- **The one real duplication risk was eliminated before adding prediction, not after**: `Explorator._simulate_movement` used to inline the entire per-axis collision-tested movement + facing/animation logic. It's now `Explorator._resolve_movement_step(session, direction, running, dt, predicting=False)`, called both by `_simulate_movement` (real per-frame simulation, `predicting=False`) and by prediction/replay (`predicting=True`). `predicting=True` skips everything that must stay server-authoritative-only — `_update_current_room`, `_attempt_fall`/`_is_void`, footstep audio, debug-move logging — so a speculative client-side replay can never itself trigger a room transition, a fall, or a sound the server hasn't actually confirmed; only position/facing/animation are ever computed speculatively. This means server tick and client prediction share 100% of the actual collision math — no risk of the two ever computing movement differently.
- **Prediction** (`Explorator._predict_local_movement(dt)`, client-only, called every frame from `run_networked` right after `_read_input()`): assigns a monotonically increasing `seq` (`PlayerSession.next_input_seq`), buffers `(seq, direction, running, dt)` in `session.pending_inputs`, and immediately calls `_resolve_movement_step(..., predicting=True)` so the local player moves the instant a key is pressed instead of waiting a full round-trip. `seq` travels as a sibling field on the `"input"` wire message (`protocol.py`'s `input_state_to_fields`/`InputState` stay seq-free on purpose — `InputState` is generic engine plumbing, not a networking concept). `GameServer._drain_incoming` records the seq of the most recent input it actually applied as `PlayerSession.last_input_seq` (server-side bookkeeping), and `protocol.build_snapshot` echoes it back per-player as `"last_input_seq"`.
- **Reconciliation** (`Explorator._reconcile_local_player(entry)`, client-only, called from `apply_network_snapshot` for the local player's own entry instead of the old blind overwrite): resets `position`/`health` to the server's authoritative values for that tick, prunes every buffered input with `seq <= entry["last_input_seq"]` (now confirmed), then replays whatever's left via `_resolve_movement_step(..., predicting=True)`. In the normal case (no divergence) the replay reconstructs the exact same position that was already on screen, so there's no visible correction at all; a genuine mismatch (a collision the client didn't know about yet) corrects immediately on the next snapshot, with no additional lerp of the correction itself — confirmed as the preferred trade-off over smoothing corrections.
- **Real bug found right after shipping the above, fixed the same day**: idle/walk/run animation visibly jumped and skipped frames during play. Root cause was reconciliation treating `action`/`animation`/`frame` exactly like `position` — snap to the server's value, then let replay "reconstruct" the rest — but unlike position (idempotent: each replay pass starts from a fresh authoritative baseline), `Player.update(dt)`'s frame advancement mutates a cumulative `animation_timer` that the snapshot never carries and that replay never resets. Since a buffered input can get replayed multiple times (once per snapshot until the server acks its seq), each replay pass was calling `player.update(dt)` again for time that had already been counted — on top of `_reconcile_local_player` also force-setting `player.frame` back to a stale, 30Hz-tick-quantized server value every snapshot. Fixed two ways: (1) `_resolve_movement_step` gained `advance_animation=True` — only `_predict_local_movement`'s real, once-per-real-frame call still advances `player.update(dt)`; the replay loop in `_reconcile_local_player` now passes `advance_animation=False`, so animation is never double-counted no matter how many times an input gets replayed. (2) `_reconcile_local_player` no longer touches `action`/`animation`/`frame` at all while the player is just walking/idling — those are continuous, purely cosmetic, client-driven state with nothing for the server to arbitrate. They're only ever pulled from the snapshot while a one-shot action is genuinely in play (`entry["action"]` or the local player's own `.action` is not `None`), since attack/interact/jump are the one thing that's still never predicted and must come from the server. Verified with a dedicated idle-animation regression script: 3 simulated seconds of standing still, snapshots arriving faster than input sends (to force frequent reconciliation/replay churn) — frame advanced exactly 20 times, matching `3.0s / Player.animation_speed(0.15s)` exactly, where the old code inflated this well beyond that.
- **Remote-entity smoothing**: every mirrored *non-local* entity (other players, animals, enemies, pickups, item pickups, dynamite, explosions) no longer has its `.position` snapped directly from a snapshot. `apply_network_snapshot`'s per-entity updaters (`_apply_animal_entry` etc., now instance methods instead of `@staticmethod` so they can reach `self`) call `_register_network_target(entity, x, y)` instead, which records `self._network_targets[id(entity)] = (entity, x, y)` — rebuilt from scratch on every snapshot (simpler than incremental invalidation, and immune to stale references when an entity despawns, since `_sync_mirror_list` already handles add/remove of the mirror objects themselves). `Explorator._smooth_network_entities(dt)`, called once per render frame from `run_networked` (not server-side), eases every target's owner `.position` a `NETWORK_INTERP_RATE`-controlled fraction of the way there — a plain per-frame lerp, not a timestamped double-buffer, judged sufficient for LAN co-op. A brand-new mirror object (`_sync_mirror_list`'s `factory(entry)` branch) has its position snapped straight to the entry's `(x, y)` *before* being registered as a target, so a newly-appeared entity doesn't visibly lerp in from whatever placeholder position its constructor used.
- **Cleanup folded into this phase** (motivated by touching `run_networked`, not a separate audit): `run()` and `run_networked()` used to each inline an identical QUIT/mouse-wheel-zoom/F3 event block. Extracted into `Explorator._handle_shared_debug_event(event)`, returning `"stop"` (caller's loop should end — QUIT only), `"handled"` (consumed, loop continues), or `None` (not one of these, caller keeps checking its own event chain) — both `run()` and `run_networked()` now call it first and only implement what actually differs (TAB/F4/ESC handling, per-session dispatch).
- **Verified with an ad hoc localhost script** (`GameServer` in a background thread + a real `NetworkClient`, same spirit as Phase 3's own two-process smoke test): asserted the local player's position changes from a single `_predict_local_movement` call *before* any snapshot has been received (proving prediction isn't waiting on the round-trip), and that `pending_inputs` stays bounded and drains to empty over many predict+send+reconcile cycles (proving the server is acking every input and the client is pruning correctly, not leaking a growing backlog). Not a permanent test in the repo (none exists, see Commands) — a one-off verification script.

**`WorldRenderer` tile-seam fix (unrelated to multiplayer, found via user report) — done:** at any zoom level where `tile_size * zoom` isn't a whole number (i.e. everywhere except the exact `min_zoom`/`max_zoom` bounds — every level in between, reached via `Camera.zoom_at`'s `*1.2`/`*0.8` steps, is fractional), tiles were positioned independently via `camera.world_to_screen`, each blit truncated to an integer pixel position on its own — so consecutive tiles stepped by `floor(tile_px)` some of the time and `ceil(tile_px)` other times (whichever the accumulated fractional position crossed), while the cached tile texture stayed a single fixed rounded width. Whenever the step exceeded the texture's width, a 1px gap flickered in — an irregular grid that tracked the logical tile grid, matching the user's report exactly (present at every zoom except min/max, where `tile_px` happens to already be a whole number). Fixed by computing one shared, already-rounded screen-space origin per `render()` call and positioning every tile as `origin + x * tile_px` (`tile_px` itself now `round()`-ed once) instead of re-deriving each tile's position independently — adjacent tiles are now always exactly contiguous, at any zoom. Verified by rendering across a spread of zoom levels (including the exact fractional ones `zoom_at` produces) headlessly with no crash; the fix itself is a straightforward algebraic guarantee (every tile is an integer multiple of the same rounded `tile_px` from the same origin), not something that needs a runtime assertion.

**Multiplayer refactor, Phase 5 — server-authority hardening (protocol robustness, not position/damage anti-cheat) — done:**
- **Scope clarified before starting**: since the server already reuses the full `Explorator` simulation (Phase 3), position/collision/damage/pickups were already never trusted raw from a client — nothing to harden there. What Phase 5 actually closes are protocol-robustness gaps: a malformed message that could crash the shared tick loop, no rate limiting, `pvp_toggle` reachable by any client, no connection cap.
- **Two distinct tolerance mechanisms, not one generic counter** (deliberate, decided with the user via AskUserQuestion): unreadable JSON (not even valid JSON — `protocol.decode` itself fails) stays strict, immediate disconnect, in `GameServer._handle_connection`'s reader thread — a client using our own `protocol.encode()` should never produce this except when broken/hostile, so there's no legitimate case to tolerate. Structurally-invalid-but-valid-JSON (wrong types, missing fields, out-of-range values — new `protocol.validate_message(payload)`, raises `ValueError`/`TypeError`) gets bounded tolerance instead: a per-connection `invalid_streak` counter, local to that connection's own reader thread (no cross-thread state needed — one thread per connection), resets on any valid message, disconnects after `INVALID_STRIKE_LIMIT` (10) *consecutive* failures. `_apply_message` (the main tick thread's per-message dispatch, extracted from the old inline `_drain_incoming` body) still wraps application in its own `try/except (KeyError, ValueError, TypeError)` as a defense-in-depth net — no single message, validated or not, can ever crash the shared tick loop.
- **Rate limiting is measured where ticks actually happen**, not in a reader thread that has no notion of the server's tick rate: `_drain_incoming` now groups queued messages by `player_id` before applying them, and if a player exceeds `MAX_MESSAGES_PER_TICK` (15 — generous headroom over an honest client's ~2 `input` messages/tick at 60fps client / 30Hz server) it still applies the allowed head (not a full-tick starve) and increments `self._flood_strikes[player_id]`; falls back to 0 the moment a tick is under the cap again (an isolated burst doesn't count against a client). `FLOOD_STRIKE_LIMIT` (5) *consecutive* over-cap ticks (~165ms of sustained flooding) triggers a disconnect.
- **New `GameServer._kick(player_id, reason)`**: since the flood check can only ever fire on the main tick thread (not the connection's own reader thread, unlike the invalid-message case above), disconnecting needs to reach across threads. Rather than duplicating `_handle_connection`'s cleanup, `_kick` just shuts down that connection's raw socket (`conn.shutdown(socket.SHUT_RDWR)`, same reasoning as `NetworkClient.close()`'s own Phase-3-documented fix) from the main thread — that unblocks the reader thread's blocked `readline()` (EOF/OSError), which then runs through the *exact same* `finally` cleanup as any ordinary disconnect. Needed a new `self._connections: {player_id: raw socket}` (populated/cleared alongside `self._clients`) so the main thread can reach a connection's socket at all.
- **`pvp_toggle` restricted to the "host"** — `GameServer._host_player_id()` returns `min(self.explorator.players.keys(), default=None)`, i.e. whichever *currently connected* session has the lowest `player_id` (ids are assigned in increasing connection order, never reused). Deliberately not a literal fixed id-0 check: if the very first-connected player disconnects, the ability to toggle PvP would otherwise be permanently stranded for the rest of the server's life. "Host" is recomputed live, so it correctly moves to the next-lowest still-connected player.
- **`--max-players`** (`GameServer(..., max_players=4)`, new `main.py` flag, default 4): checked in `_handle_connection` right after validating the `join` message and *before* a `player_id` is ever consumed or a session created — a rejected connection gets a new `protocol.MSG_SERVER_FULL` message instead of `welcome`, then the socket is closed. Client-side, `NetworkClient.wait_for_welcome()` recognizes it and raises a new `ServerFullError` immediately instead of waiting out the generic 5s timeout; `main.py`'s `run_client` catches it alongside `TimeoutError`.
- **Locking scope widened, on purpose**: `self._clients_lock` already guarded `self._clients` (mutated by connection threads, read by the main thread's broadcast). `self._connections` and `self._flood_strikes` are in the exact same situation (populated/cleared by a connection thread, read/mutated by the main thread) — both now go under the same lock, rather than relying on the CPython GIL to make plain dict mutations safe across threads by accident.
- **Real bug caught by verification, fixed before landing**: the first implementation put `protocol.decode()` and `protocol.validate_message()` in the *same* try/except in `_handle_connection`'s reader loop — meaning unreadable JSON accidentally got the tolerant "streak" treatment too, instead of the intended strict immediate disconnect. Caught by a dedicated ad hoc test asserting a single garbage (non-JSON) line disconnects right away — it didn't, revealing the bug — fixed by splitting them into two separate try/except blocks, exactly matching the design each was supposed to have per the plan.
- **Verified with ad hoc localhost scripts** (raw sockets standing in for a misbehaving client, since `NetworkClient` itself only ever sends well-formed messages): `--max-players` rejection without consuming a `player_id`; a flooding client eventually kicked, unrelated clients unaffected; consecutive invalid messages disconnecting after the limit, with a valid message in between provably resetting the streak; a single unreadable line disconnecting immediately while the server stays usable for everyone else; `pvp_toggle` ignored from a non-host, applied from the host, and correctly handed to the remaining player once the original host disconnects (polled for the server-side session removal rather than a fixed sleep, to avoid timing flakiness). Also re-ran Phase 4's own prediction/reconciliation smoke test afterward to confirm no regression from touching `server.py`.

- **`core/data/progression.py`** (new): `MAX_LEVEL = 100`, a quadratic XP curve (`XP_CURVE_FACTOR`, `xp_for_level`/`level_for_xp`), per-event XP grants (`XP_ENEMY_KILL`, `XP_ANIMAL_KILL`, `XP_DUNGEON_CLEAR`), and `UNLOCKS`/`unlocked_objects(level)` -- a level-threshold -> newly-unlocked-object-types table (all placeholder values, freely retunable, one file). **Multiplayer refactor, Phase 6c — real split-screen, per-session room/floor tracking, and E/S (gate/wall) link desync fixes — done:**
- **Real bug found and fixed, independent of the rest of this phase**: `DungeonAssembly.room_at(floor, x, y)` (used by `check_button_trigger` to resolve a button's `assembly_links` across rooms) had no disambiguation -- for a doorway merged on the *same* floor, both the anchor and candidate rooms' bounding boxes legitimately contain the shared door cell, and `room_at` always resolved to whichever was inserted first (the anchor), so a button in the anchor room could never actually open the candidate's copy of the door (the reverse direction happened to work by coincidence). Reproduced in the checked-in `assets/donjons/donjon_002.json`. Fixed at the source instead of patching `room_at`: `generate_assembly`'s two `assembly_links`-building loops now stamp the already-known target room index directly (`"room": candidate_index` / `"room": anchor_room.index`) onto each entry, and `check_button_trigger` prefers that explicit index over the ambiguous `room_at` lookup (kept as a fallback for donjons saved before this fix -- additive field, same convention as `variant`/`links`/`open`).
- **Compounding bug, also fixed**: `resolve_room_transition` switched `current_placed_room` to the target room the instant a player's feet landed on a shared door cell, without ever checking the *destination* copy's own `open` state -- if the two copies were desynced (by the bug above, or a stale hand-saved room file), the player would cross successfully (the source side was open) and then find themselves wedged against a still-closed destination copy on the very next walkability check. This is exactly the "stuck inside a wall after taking an open door" symptom reported. Fixed with a self-healing sync in `resolve_room_transition` itself: if the source door read `open`, the destination copy's `open`/`activated`/`frame` are forced to match at the moment of crossing -- corrects already-generated/saved donjons at play time too, no regeneration needed.
- **`current_placed_room`/`last_door_obj` moved from `Explorator` (one shared value for the whole session) to `PlayerSession` (one per player)** -- the root architectural gap behind "a joueur qui change de room casse l'autre": with a single shared value, one player crossing a door silently changed which room/floor *every* session's collision and rendering used. `Explorator.current_placed_room` still exists but now means only "the room a freshly-joining session should spawn into" (set once by `open_room`/`open_donjon`, read by `add_network_session`/`_spawn_new_session_at_start`) -- every per-frame read/write (`_update_current_room`, `_attempt_fall`, `_current_room_and_offset`, `_is_cell_walkable`/`_is_void_at`/`_is_void`, `_resolve_buttons_and_health`) goes through the calling session's own `current_placed_room` instead, all of which already had a `session` in hand at the call site (no loop restructuring needed, just threading the value one level deeper). New `Explorator._spawn_new_session_at_start(session)` factors out the "place a session that's joining after the fact" logic shared by `add_network_session` and `_maybe_join_secondary_keyboard_player` -- the latter used to leave a newly-joined local player 2 with no `current_placed_room` at all, which would have crashed the first time they rendered.
- **Combat/pickups/animal aggro made floor-*plural*-aware**: `_rooms_with_offset` now takes an explicit `floors` set (`_active_floors()`, the union of every session's own floor) instead of one implicit floor, so `_visible_animals_global`/`_visible_enemies_global`/`_collect_pickups` see every floor a player actually occupies, not just one. `DungeonAssembly.update`'s `player_floor` scalar became `player_refs_by_floor` (a `{floor: [PlayerRef, ...]}` dict, built by `Explorator._player_refs_by_floor`) -- previously a second player on a different floor would get every other floor's animals/enemies aggroing on a meaningless translated coordinate while their *own* floor's animals never even saw them.
- **Real split-screen for local co-op, replacing the old zoom-to-fit shared camera**: `PlayerSession` gained its own `camera` (a real second `Camera` instance, no shared state risk). `Explorator._viewport_rects()` splits `self.screen` into vertical slices, one per local session (`input_source_kind != "network"` -- a networked client's remote-mirror sessions never get a viewport); `render()`/`_render_viewport(target, camera, room)` draws into a real `screen.subsurface(rect)` per viewport (a new pattern for this codebase, but the existing `Dungeon.render`/`DungeonAssembly.render`/entity `.draw` calls all already take `screen`/`camera` as plain parameters, so nothing about them needed to change). `_draw_debug_hitboxes`/inventory panels follow the same per-viewport split.
- **"Merge screen" -- the shared camera comes back automatically when local players share a room, added after the user tried real split-screen and found it disorienting to stay on permanently**: `_merged_view()` is true for solo, single-room mode (only one room ever exists there), or 2+ local sessions currently in the *exact same* `current_placed_room` -- `self.camera` (the original Phase 2 zoom-to-fit logic, revived as `_update_shared_camera`) drives one full-screen view in that case; the instant one player crosses into a different room, `_merged_view()` flips to false and real split-screen (per-session cameras/viewports) takes over on its own, no manual toggle. `render()`/`_draw_debug_hitboxes`/mouse-wheel zoom/inventory-panel regions all branch on this the same way.
- **Real bug found and fixed, client-side networked room tracking**: room/floor crossings are deliberately never predicted client-side (only the server decides them) -- but nothing was actually telling the client which room its own player (or anyone else's) was really in, so `session.current_placed_room` silently stayed frozen at the spawn room forever once it became load-bearing for both rendering (`active_floor`) and local movement prediction's own collision checks. This produced exactly the reported "first room stays active forever, player falls through masked floors" symptom. Fixed by adding each player's room to the snapshot (`protocol.build_snapshot`'s `"room"` field, a `PlacedRoom.index`) and consuming it client-side for both the local session (`_reconcile_local_player`) and every remote mirror (`apply_network_snapshot`), via a new `Explorator._room_for_ref(room_ref)`.
- **Verified throughout with real client/server processes, not just unit-level fakes**: a live `GameServer` + two real `NetworkClient`s reproducing the exact reported crash (a second player's mirror session with no `current_placed_room`, then a real `_predict_local_movement` call) and the room-tracking bug (server-side session forced into a second room, client's local session confirmed to follow via the next snapshot, `render()` confirmed not to raise afterward) -- both previously failed exactly as reported, both pass now.

**Multiplayer refactor, Phase 6e (partial) — host/join from home over LAN, retiring `--server`/`--connect`, and an in-game chat/command console — done:**
- **Scope, confirmed with the user**: hosting means the host's own game connects to its own server as a normal `NetworkClient` over loopback (`127.0.0.1`) -- the host plays their own hosted world exactly like any other connected player, reusing 100% of existing client code (prediction, chat, rendering) with zero special-casing, at the cost of a tiny loopback round-trip for the host's own input too. A separate local-authority path (host bypasses the network entirely) was explicitly not built.
- **Real technical blocker found and fixed before anything else could work**: `core/network/server.py` used to force `SDL_VIDEODRIVER=dummy`/`SDL_AUDIODRIVER=dummy` at **module import time** and `GameServer.__init__` always called `pygame.display.set_mode((1, 1))` -- both assumed the process had no real window, which would have corrupted/replaced the actual game's display the instant `GameServer` was constructed from inside the normal windowed process. Fixed: the env-forcing moved out of module scope entirely; `GameServer.__init__` gained an optional `screen=` param -- when given (hosting-in-process), it skips `pygame.init()`/its own display setup and reuses the passed screen; `screen=None` (nobody passes it anymore, but the branch is still exercised by the ad hoc verification harness) keeps the original standalone headless behavior, dummy-driver env vars and all, scoped to that one code path instead of the whole module.
- **`--server`/`--connect` removed from `main.py` entirely**, per the user's explicit "these launches shouldn't exist anymore" -- `main()` is back to exactly what it was before Phase 3 (`GameManager(screen, settings).run()`), no `argparse`. `GameServer`/`NetworkClient`/`run_networked` are unchanged and fully reused, just driven from the new in-game flow below instead of CLI flags -- nothing is lost as *code*, only as a CLI surface (a pure headless dedicated server with no local player attached is no longer reachable without writing a small script against `GameServer` directly).
- **New `core/network/discovery.py`**: plain UDP, host-announces / client-listens (like Minecraft's own LAN world discovery), not request/response. `HostAnnouncer` broadcasts a small JSON packet (name/tcp_port/room_kind/room_name) to the LAN every second while hosting; `SessionBrowser` collects announcements (deduped by `(source_ip, tcp_port)`) and expires anything not re-announced within 5s. No internet/friends-list component -- pure local-network broadcast, explicitly future work.
- **`Explorator.start_hosting()`/`join_session()`/`stop_networking()`** (new): `start_hosting` builds a `GameServer` hosting whichever single room is currently open (home, in practice -- see below), runs it on a daemon thread, starts a `HostAnnouncer`, then connects a loopback `NetworkClient` and finishes exactly like `join_session` does for someone else's session (`_finish_connecting`, factored out of both -- mirrors `main.py`'s old `run_client` sequence: `wait_for_welcome` -> `open_room`/`open_donjon` -> `adopt_local_player_id` -> hand the live client to `GameManager`). `stop_networking` doesn't try to unwind every bit of network-driven state by hand -- it tears down the client/server/announcer and has `GameManager` build a **fresh `Explorator`**, the same object graph a brand-new app launch's own `__init__` would produce, then sets `boot_into_home` so the next trip through `Menu.run()` redirects there again.
- **`GameManager`** gained `network_client`/`_game_server`/`_host_announcer` (all `None` until hosting/joining starts); `run()`'s `EXPLORATION` branch calls `explorator.run_networked(network_client)` instead of `explorator.run()` whenever `network_client` is set -- the one dispatch change needed, `Explorator` itself needed no awareness of how it got connected.
- **New `MultiplayerPanelUI`** (`core/exploration/multiplayer_ui.py`, alongside `inventory_ui.py` as Explorator-only overlay UI): `M` toggles it (a hardcoded key, same convention as TAB/ESC/F3/F4 -- `Settings.ACTIONS` is specifically for per-device rebindable *gameplay* actions, not global UI toggles). Not-yet-connected: a live `SessionBrowser`-backed list with "Rejoindre" per entry, plus "Heberger cette partie" -- only openable while `Explorator._is_home_room()` (factored out of `_check_home_zoom_switch`, which now calls it too) so hosting/joining really is "from home only," matching the original pitch. Once connected: status text + "Deconnecter", reachable from `run_networked()` too (no home restriction there -- makes sense to check status/disconnect from anywhere while already playing). `handle_event` drives `Explorator`'s connection methods directly (not the "return an action, caller applies it" shape `GeneratorPanelUI`/`RoomPanelUI` use) and returns `"connected"`/`"disconnected"`/`None` so `run()`/`run_networked()`'s own event loop knows to stop looping and let `GameManager`'s dispatch pick up the change -- the panel has no access to that loop's own `running` local to do it itself.
- **Chat + slash-commands**: new `protocol.MSG_CHAT` (`"text"`, capped at `MAX_CHAT_TEXT_LENGTH`). `GameServer._apply_admin_command`'s old if/elif ladder was extracted into `_dispatch_command(line, requester_player_id=None)`, returning an optional reply string instead of printing directly -- shared by the trusted stdin admin console (`requester_player_id=None`, everything allowed) and a chat-originated `/...` message, which additionally gates `PRIVILEGED_COMMANDS` (`level`/`kick`/`stop`/`shutdown`/`kill`) to `_host_player_id()` only; `list`/`help` stay open to everyone. A command's reply goes back privately to the requester alone (new `GameServer._send_to`, `_broadcast`'s single-client counterpart) -- nobody else needs to see a rejection or a level-up confirmation. Plain (non-`/`) text broadcasts to everyone under the sender's profile name. Client side: `T` (network play only -- solo `run()` never wires it, nobody to talk to) opens a text box following `Menu`'s own name-entry input pattern exactly (backspace, printable-char filter, length cap, blinking cursor); while open, a **new top-of-loop guard** in `run_networked()` (checked before F4/ESC/session dispatch, since research confirmed nothing already swallows raw events this way) routes every KEYDOWN into the buffer instead, so a keystroke while typing can never also toggle PvP or open the menu. Received chat renders as a simple bottom-left scrollback (`Explorator._render_chat`, no new widget class -- simple enough not to earn one).
- **Real pre-existing bug found and fixed, exposed by this work, unrelated to hosting/chat mechanics themselves**: `GameServer._handle_connection`'s reader loop used `conn.makefile("rb").readline()` combined with `conn.settimeout(READ_POLL_TIMEOUT)` to poll for kicks -- a genuinely idle connection (no message for over a second) disconnected outright. Root cause: `socket.makefile()`'s buffered reader permanently "taints" itself the first time the underlying socket read times out, and raises a plain `OSError("cannot read from timed out object")` on every read after that instead of a clean, retryable `socket.timeout` -- a documented CPython gotcha. This was already latent in the Phase 5 code (the polling design has been there since then) but never actually triggered: every previous smoke test kept connections busy with constant `input` traffic (a real player sends one every rendered frame), so the read never idled long enough to time out even once. Hosting-from-home made a genuinely idle connection common (sitting in a menu/panel, or simply standing still) and immediately exposed it -- caught by an ad hoc idle-connection test, not by inspection. Fixed by replacing the buffered `makefile()` reader with a small manual line-assembler over raw `conn.recv()` (`GameServer._recv_line`, using a 1-element list as an in/out buffer parameter so bytes already received are never lost if a later `recv()` in the same line times out) -- raw `socket.recv()` doesn't have the taint problem, it raises `socket.timeout` reliably on every call.
- **Verified**: `python -m py_compile` on every touched/new file; the headless smoke test; an ad hoc `HostAnnouncer`/`SessionBrowser` localhost test (discovery + expiry); a real host-and-join localhost test (a real `GameManager` hosting via `Explorator.start_hosting`, plus an independent raw `NetworkClient` joining) covering plain chat broadcast with sender name, a privileged command rejected from the non-host and succeeding from the host, an unprivileged command working for anyone, `/kick` actually disconnecting its target, and `stop_networking()` clearing every network field, handing back a fresh `Explorator`, and releasing the port. The idle-connection bug above was caught mid-verification when an early version of this same test (with no chat/commands sent yet, just hosting + joining + waiting) still failed -- a `drain_for` test-harness bug (an over-eager early-return on the first matching message type, missing a genuine reply that arrived slightly later behind an already-queued stale one) was found and fixed the same way, by collecting the full time window instead of stopping at the first match.
- **Explicitly out of scope, not silently dropped at the time**: the dungeon-entrance "sync barrier" -- done the same day, see directly below; friends list / non-LAN discovery; reconnection after a dropped connection (unchanged from Phase 3's original decision).

**Multiplayer refactor, Phase 6e (continued) — kicked-client detection fix, and the dungeon-entry sync barrier — done:**
- **Real bug fixed, reported by the user after trying the host/join feature live**: a kicked (or otherwise disconnected) player's own client never noticed -- `run_networked()` had nothing checking the connection's health, so it kept predicting/rendering the now-abandoned world forever from that player's point of view, even though the server had already dropped their session. Fixed with a new `NetworkClient.is_connected` property (`self._running`, already flipped False by `_read_loop`/`send` on any socket failure) checked once a frame in `run_networked()`, right after draining messages -- on connection loss it sets `game_manager.state = GameState.MENU` and breaks, the same "no final frame rendered" pattern every other state-changing exit here already follows (TAB/ESC don't render one last frame either, so this isn't a new inconsistency).
- **Sync barrier for `dungeon_entrance` crossings** (the deferred piece from the previous Phase 6e entry -- "une fois que tout les joueurs ont passe l'entree... on les fait apparaitre dans le donjon genere"): crossing the entrance no longer generates immediately -- it marks that `player_id` "ready" (`Explorator.dungeon_entrance_ready`, a set) and freezes that session in place (same per-session freeze slot `session.inventory_open` already uses in `update()`'s per-player loop) until **every currently connected player** has also crossed. Solo play is unaffected in practice: with exactly one session, that one crossing already satisfies the barrier the same frame, identical to the old immediate-trigger behavior.
- **Real pre-existing gap found and fixed while wiring this, not by this entry but exposed by finally exercising a real multiplayer crossing**: the original `_check_dungeon_entrance` read `self.settings.local_player_name` to find generation parameters -- which is **always `None` on the server** (`_HeadlessGameManager.settings = None`), meaning the trigger silently never fired at all in real multiplayer, only in solo play where it happened to share the same Explorator/Settings instance as rendering. Fixed with new `Explorator._dungeon_entrance_source_profile()`: uses the **host's** saved `generator_room_names`/`generator_room_count` (lowest `player_id`, matching `GameServer._host_player_id`'s own convention) rather than whichever profile the local client happens to have -- works identically in solo (the one session already is the host) and on a real server (every session's own `Profile` is already loaded via `add_network_session`), and keeps the generated result independent of crossing order.
- **Thread-safety consideration that shaped the design**: completion is checked **every frame**, unconditionally, from a new `Explorator._maybe_complete_dungeon_entrance_barrier()` (called first thing inside `_resolve_dungeon_transitions`, not only reactively inside `_check_dungeon_entrance` the moment someone crosses) -- specifically so a player disconnecting while others are still waiting can complete the barrier for whoever's left, without requiring anyone to cross again. `remove_session` itself deliberately does *not* trigger this check directly (it only discards the departing id from the ready set) -- on the server, `remove_session` runs from that connection's own reader thread, where touching shared world state via `generate_assembly`/`_enter_assembly` would be unsafe; only the main tick thread's own `update()` call ever reaches the completion check.
- **A failed completion attempt (no saved selection, or nothing in the pool has a spawn+exit) clears the ready set instead of leaving everyone stuck frozen** -- they un-freeze on their own next frame, at the cost of needing to cross again once whatever was wrong (e.g. the host's empty generator pool) is fixed.
- **Client visibility**: new `protocol.build_snapshot` field `"dungeon_entrance_ready"` (sorted player_ids) -- a client (including the host's own, since even hosting connects via loopback as a normal client, see the previous Phase 6e entry) never runs the barrier logic itself, only the server/solo-local Explorator does inside `update()`, so this is the only way any client learns to show progress at all; mirrored 1:1 onto `self.dungeon_entrance_ready` in `apply_network_snapshot`, same pattern `victory`/`pvp_enabled` already use. New `Explorator._render_dungeon_entrance_barrier()`: a small top-center "En attente des autres joueurs : X/Y prets" banner, shown only while `0 < ready < total` -- never in solo play, where that state is never held long enough to render.
- **Verified**: `python -m py_compile`; the headless smoke test; the existing host/join/chat/kick localhost regression suite re-run clean; a new ad hoc script driving `Explorator._check_dungeon_entrance`/`_maybe_complete_dungeon_entrance_barrier` directly (no real sockets needed, the barrier is pure Explorator-level state) covering: solo single-crossing still triggers immediately; two sessions -- the first crossing freezes and does *not* generate, the second completes it; and a session disconnecting after the first crossing (but before the second ever crosses) completes the barrier for the sole remaining player via the per-frame check alone.
- **Real usability bug found and fixed the same day, reported by the user actually trying to test the barrier**: a single-cell doorway can only ever hold one hitbox, so the first player to cross was left frozen exactly *on* the door tile, permanently blocking every other player from ever reaching that same cell to cross it themselves -- nobody but the first player could ever actually trigger the barrier. Fixed two ways: (1) `_is_walkable`'s player-vs-player check now excludes anyone in `dungeon_entrance_ready` entirely, and both render entity-gathering sites (`_render_viewport`'s single-room and assembly-mode player lists) skip them too -- a waiting player stops colliding *and* stops rendering, freeing the tile visually and physically for the next crosser. (2) A waiting player wasn't stuck with no way out either: any movement input now backs them out on their own (`update()`'s per-session loop checks `session.input.move_direction` for a waiting session), via new `Explorator._cancel_dungeon_entrance_wait` -- clears their ready/edge-trigger state and repositions them one cell onto the room-interior side of the door (new module-level `_doorway_interior_offset(dungeon, x, y)`, the same up/down-vs-left/right FLOOR-neighbor shape `ObjectManager.is_valid_doorway` itself checks) instead of leaving them exactly on the door tile they just tried to take.
- **Verified**: a new ad hoc script confirming `_doorway_interior_offset` points to the correct room-side neighbor, a waiting player is excluded from both `_is_walkable`'s collision check and the render entity list while a non-waiting session is unaffected, and `_cancel_dungeon_entrance_wait` clears ready state and repositions correctly, with a fresh crossing afterward able to re-trigger normally.

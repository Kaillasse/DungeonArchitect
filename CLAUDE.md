# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Dungeon Architect — a top-down, tile-based roguelike editor/game built with pygame. Players will explore procedurally-composed dungeons and unlock tiles/monsters/traps/entities for a fully customizable, destructible home base between runs. See `DA.txt` (French) for the full design pitch and current priority list.

The grid uses 16x16px source art; each world grid cell renders that art at 2x, so a logical cell is 32x32px (see `core.data.ressources.WORLD_SCALE`). Single rooms are saved as JSON under `assets/rooms/`; procedurally-assembled multi-room dungeons under `assets/donjons/` (see Roadmap).

## Commands

- Run the app: `python main.py` (opens the main menu, `GameState.MENU`).
- Dependencies: `pygame==2.6.1`, declared in `requirements.txt`. **That file is UTF-16LE encoded** (not UTF-8) — `pip install -r requirements.txt` may fail to parse depending on pip version; if so just `pip install pygame==2.6.1` directly. A `.venv` already exists in the repo root.
- Headless smoke-test of the editor: set `DUNGEONARCHITECT_HEADLESS=1` before running — `GameManager` skips the menu and starts straight in `GameState.CREATOR`, and `Creator.run()` saves the current room and exits immediately instead of opening the pygame window/event loop.
- There is no test suite, linter, or build config in the repo.

## In-app controls

- Menu: `UP`/`DOWN` (or `Z`/`S`) to move the selection, `ENTER` or mouse click to confirm, `ESC` quits. Choosing "Editeur de salle" or "Explorer" opens a room-picker (see Architecture) before actually entering that state — "+ Nouvelle salle" (Creator only) starts a fresh untitled room.
- Editor (Creator): left-click an empty floor cell to paint, left-click-drag an already-placed object's body to move it, left-click-drag a linkable object's indicator dot (top-right corner of its tile — `button`/`gate`/`wall`) onto another one's dot to link them, drag object icons from the palette onto the grid to place new ones, right-click erase, mouse-wheel zoom, `TAB` switch to exploration, `ESC` back to menu (or, while previewing a generated dungeon, closes the preview first — see below). The Sauvegarder/Charger/Supprimer panel (top of screen) replaces the old F1-F4 console shortcuts entirely — "Charger" lists both rooms (`[Salle] name`) and saved dungeons (`[Donjon] name`) together. Below it (left column, under the tool/object palettes) is the generator panel: a room pool (checkbox-style multi-select, defaults to every saved room) and a room count (+/- stepper); "Generer" runs the procedural assembler, saves the result to `assets/donjons/`, and immediately shows it — while previewing, painting/object tools are suspended (they act on the normal single-room `Dungeon`, which isn't what's on screen).
- Exploration (Explorator): French AZERTY movement (`Z`/`Q`/`S`/`D`, not WASD), hold `SHIFT` to run (faster movement + `run` animation instead of `walk`), left-click to attack, right-click to interact, `SPACE` to jump (one-shot animations — see Roadmap), mouse-wheel zoom, `TAB` back to editor, `ESC` back to menu. Walking onto a linked `button` opens whatever `gate`/`wall` it's linked to.

## Architecture

`main.py` builds the pygame `screen` and hands it to `GameManager`, whose `run()` loop dispatches on `core.engine.gamestate.GameState` (`MENU` / `CREATOR` / `EXPLORATION`). Each state object owns **its own inner pygame event loop** (`Menu.run()`, `Creator.run()`, `Explorator.run()`) rather than there being one shared frame loop — switching state means setting `self.state` and breaking out of the current inner `while` loop, which returns control to `GameManager.run()` to dispatch into the next state's loop.

Package layout (`core/`):
- `engine/` — state machine plumbing: `GameManager` (also owns `pending_room`, set by `Menu`'s room-picker before switching to `CREATOR`/`EXPLORATION`; `run()` applies it via `creator.open_room()`/`explorator.open_room()` right before dispatching into that state's loop), `GameState`, `Camera` (world↔screen coordinate/zoom transform), `RoomManager` (thin wrapper around `Dungeon.save_to_json`/`load_from_json`/deleting a room file, plus `scan()`/`next_new_room_name()` — holds no "current room" state itself, that's each caller's concern; no console I/O, unlike its previous `input()`-driven incarnation).
- `editor/` — the room editor (`Creator`, the `CREATOR` state): `ui.py` has `ToolPaletteUI`, `ObjectPalette` (the draggable object-type icon tray, reuses `object_manager.load_object_frames`), `RoomPanelUI` (Sauvegarder/Charger/Supprimer buttons, each opening a `core.ui.RoomBrowser` + "Valider" button — `handle_event()` returns `(mode, selection)` once confirmed; for "load", `selection` is a `(kind, name)` tuple (`"room"` or `"donjon"`), since "Charger" lists both; for "save"/"delete" it's a plain room name), `GeneratorPanelUI` (a multi-select `RoomBrowser` for the room pool, a room-count stepper, and a "Generer" button — `handle_event()` returns `(room_names, room_count)` once confirmed, letting `Creator` call `generate_assembly()`, save it, and preview it); `tools.py` has `ObjectTool` (drag state for placing an object from the palette onto the grid); `autotile.py` is the tile-logic core (see below).
- `world/` — the dungeon data model: `dungeon.py` (`Dungeon` owns `width`/`height`/`logical_grid`/`sprite_grid` directly and orchestrates an `ObjectManager` + `WorldRenderer` + `SaveManager`; grid↔world coordinate conversion; `is_rect_walkable`/`update(dt)` delegate to `ObjectManager` — it draws nothing, saves nothing, and doesn't manage objects itself), `object_manager.py` (`ObjectManager(dungeon)` — takes the dungeon it belongs to; the `OBJECT_TYPES`/`OBJECT_LIST` registry of placeable object metadata — asset path, placement surface, footprint size in cells, frame count, and the gameplay flags `walkable`/`blocks_movement`/`blocks_until_open`/`linkable`; `get_object_at()` is footprint-aware (matches any cell a multi-cell object like `wall` covers, not just its origin); `is_cell_walkable()` is the single source of truth for whether a cell can be walked into, and `is_foreground_object()` the one for whether an object draws in front of / is walkable-despite-being-on-a-wall (currently: an L/R torch only, not the plain straight one); `check_button_trigger()`/`update(dt)` drive button→gate/wall activation and its frame-by-frame animation (holds on the last frame once reached — doesn't loop); `load_object_frames()` slices a sprite sheet, shared by the editor palette and the renderer), `assembly.py` (the procedural room-to-room assembler — see Roadmap), `entities.py` (`Player` — sprite-sheet animation keyed by direction, mirrors left-facing sprites from the right-facing frames, hitbox anchored at the feet; `Animal`/`AnimalManager` — the first live NPCs, see Roadmap; stub `NPC`/`Enemies` classes not yet wired up).
- `data/` — `ressources.py` (asset/tileset path resolution, tile metadata JSON loading, the `ROOMS_DIRECTORY`/`DONJONS_DIRECTORY` constants, `TILE_SIZE`/`WORLD_SCALE`, `list_rooms()`/`next_new_room_name()`/`list_donjons()`/`next_new_donjon_name()`), `save_manager.py` (`SaveManager` — stateless `save(dungeon, room_name)` / `load(dungeon, room_name)`, converts a `Dungeon` to/from its JSON room file; `apply_json(dungeon, payload)` factors out the payload-application half of `load()` so the assembly loader can reuse it per-room without a room-name-based file lookup).
- `rendering/` — `world_renderer.py` (`WorldRenderer.render(screen, dungeon, camera, spawn_preview=None, hide_object_types=None, show_link_indicators=False, skip_foreground_objects=False, hide_cells=None)`: draws the tile grid with a `(tile_index, zoom)` surface cache, placed objects sized from `OBJECT_TYPES[type]["size"]` (in grid cells, not raw sprite pixels) and at their current `obj["frame"]`, debug grid lines, the spawn-preview marker, and (only when `show_link_indicators=True`, which only `Creator` passes) each linkable object's indicator dot and any persisted links. `hide_cells` (a set of local (x, y)) skips specific cells entirely (tile and object) — used by `DungeonAssembly.render()` for the see-through hole. `render_foreground_objects()` draws only objects `ObjectManager.is_foreground_object()` flags — `Explorator` calls it after drawing the player so a foreground object (an L/R torch) overlaps the player instead of the other way around; `Creator` never calls it since it draws no player sprite, so it just renders everything in one `render()` pass. Holds no world state itself — only pygame surface caches).
- `menu.py`, `explorator.py`, `ui.py` (top-level, not in a subpackage) — `Menu` (the `MENU` state: title screen with Editeur/Explorer/Parametres/Quitter, routes to `CREATOR`/`EXPLORATION` — but first through a room-picker mode reusing `core.ui.RoomBrowser`, setting `game_manager.pending_room` and `.state` once "Valider" is clicked; `ESC` from either gameplay state now returns here instead of quitting — only the menu itself quits the program), `Explorator` (the `EXPLORATION` state: player movement/collision, camera follow; `open_room(name)` loads a specific room and spawns the player in it, used both by the menu's room-picker and its own startup auto-discovery fallback `load_spawn_room()`), `ui.py` (`BorderManager`, the shared 9-slice panel renderer used by both the editor UI and `Menu`; `RoomBrowser`, a scrollable/slider-scrollable selectable room-name list, with an optional `multi_select` mode (checkbox-style, toggles into `selected_set`) — purely a list-selector, callers decide what confirming a selection means; used by `Menu`'s room-picker, `RoomPanelUI`, and `GeneratorPanelUI`).

Autotiling (`core/editor/autotile.py`), the core "logical grid" algorithm: cells are `EMPTY`/`FLOOR`/`WALL` ints. `build_walls()` does a two-pass pass over the grid — strip existing `WALL` cells back to `EMPTY`, then surround every `FLOOR` cell's empty neighbors (8-directional) with `WALL`. `resolve_sprite_grid()` then computes a 4-directional (`up`/`right`/`down`/`left`) neighbor bitmask string like `"0212"` per non-empty cell and looks up `(category, bitmask)` in `AUTOTILE_LOOKUP`, which is built at import time from `assets/tiles/tile_categories.json`, to pick the concrete sprite index.

## Roadmap

**Object placement rules — done:**
- `ObjectManager.add_object` now reads `OBJECT_TYPES[type]["placement"]` (`"floor"` or `"wall"`) instead of hardcoding `FLOOR` for every type — this also fixed a real bug where `torch` (wall-only) could never actually be placed. `gate`/`wall` use a third, custom placement (`"doorway"`, resolved by `ObjectManager.is_valid_doorway` rather than a plain lookup) — see the procedural-generation section below for why.
- `Dungeon.paint_cell` calls `object_manager.prune_invalid()` after every edit, which drops any placed object whose cell no longer matches its placement rule — so erasing a floor destroys the `gate`/`wall`/`button`/`vase`/`spawn` sitting on it, and erasing the floor that generated a wall segment destroys any `torch` mounted there too.
- `spawn` (and, since animal NPCs landed, every animal type too) is excluded from rendering during exploration: `WorldRenderer.render(..., hide_object_types=...)`, with `Explorator` passing its module-level `HIDDEN_OBJECT_TYPES` (`{"spawn", *ANIMAL_TYPES}`). `Creator` passes nothing, so both still show as their static placed-object icon in the editor.
- `torch` has variant-dependent placement (`ObjectManager._resolve_placement`/`_torch_variant`), not a single static rule: clicking a **floor** cell with a wall immediately beside it places an `L`/`R` variant (wall to the right → `R`, wall to the left → `L`); clicking a **wall** cell directly places the plain front-facing variant (no adjacent-floor requirement — this is the back-wall case). Stored as an optional `"variant"` key on the object dict (additive — old saves without it still load).

**Button/gate/wall linking — done, editor and runtime:**
- Any `button`/`gate`/`wall` (`OBJECT_TYPES[type]["linkable"]`) shows a small indicator dot at `Dungeon.object_indicator_position(obj)` (top-right corner of its cell) whenever `Creator` renders — `Explorator` never passes `show_link_indicators`, so links/indicators are invisible during exploration, per spec.
- Dragging from one indicator to another calls `ObjectManager.link()`, which records the connection symmetrically on both objects as an additive `"links"` list of `{"x", "y"}` targets (same additive-JSON-field approach as `torch`'s `"variant"` — old saves without it still load fine).
- `ObjectManager.move_object()` lets any placed object (not just linkable ones) be dragged to a new cell in `Creator` — it re-validates the placement rule at the destination, recomputes a torch's L/R variant if it moved, and retargets any other object's `links` that pointed at its old cell. `prune_invalid()` also drops links left dangling when the object they pointed at gets erased.
- At runtime: `Explorator.update()` calls `ObjectManager.check_button_trigger(grid_x, grid_y)` every frame using the player's hitbox (`hitbox.centerx`, `hitbox.bottom - 1` — not raw `player.position`, which sits exactly on the cell's bottom boundary and would floor-divide into the row below). Stepping onto an unactivated `button` sets `obj["activated"] = True` and opens (`obj["open"] = True`) every `gate`/`wall` it's linked to; it's a one-shot latch, not a toggle. `ObjectManager.update(dt)` (called from `Dungeon.update`, which `Explorator` calls every frame) advances `obj["frame"]` for any activated/open object at a fixed rate and **holds on the last frame** once reached rather than looping.
- Walkability is `ObjectManager.is_cell_walkable(x, y)`, not a raw `logical_grid` check: `button` is always walkable; an L/R `torch` is walkable because it sits on a floor cell to begin with (see placement above) and is drawn in front of the player there (`ObjectManager.is_foreground_object`) instead of behind; the plain straight torch (placed directly on a wall cell) stays a normal blocking wall decoration. `gate`/`wall` block until their `"open"` flag is set. `vase` always blocks (`"blocks_movement"`). `Dungeon.is_rect_walkable` (used for player-movement collision) delegates to `is_cell_walkable` per hitbox corner instead of checking `WALL` directly.
- `get_object_at(x, y)` is footprint-aware: it matches any cell within `OBJECT_TYPES[type]["size"]` of an object's origin, not just the origin itself. This is what makes a 2-wide `wall` object correctly block (and later open) *both* of its cells, not just the one it was placed on — it also means clicking the second cell of a wide object in `Creator` lets you grab it to move, same as clicking its origin cell. `WorldRenderer` positions a multi-cell object's sprite anchored to its footprint's left/bottom edge, not centered on the origin cell — centering a sprite wider than one cell on that cell's center would make it visually bleed half a tile into the neighbor on each side, out of alignment with what `get_object_at` actually considers blocked.
- These are all additive object-dict fields (`activated`, `open`, `frame`, `anim_timer`), so a saved room can reload with its buttons/gates already mid- or fully-triggered.

**Procedural room-to-room generation — data model, algorithm, persistence, rendering, Creator preview, and live Explorator traversal all done:**
- **A `gate`/`wall` entry-exit must sit on a real wall-doorway cell**, enforced by `ObjectManager.is_valid_doorway(x, y)`: the cell itself must be WALL, with exactly one FLOOR neighbor (the room interior) directly opposite exactly one EMPTY neighbor (the void beyond) and WALL flanking the other two sides — the shape of a clean break in a straight wall segment. This replaced an earlier, too-permissive rule (any FLOOR cell, same as `button`/`vase`) that let an E/S be dropped in the middle of a room, indistinguishable from an ordinary floor tile — which is exactly what made it ambiguous, mid-crossing, whether a given cell was "just floor" or a doorway to another room. `ObjectManager.add_object`/`move_object` both go through this check for `gate`/`wall`, and `core.world.assembly._valid_entry_exits(dungeon)` re-applies the identical check when the procedural assembler collects a room's usable connectors (shared by `PlacedRoom.entry_exits`, `_find_start_room`, and candidate selection in `generate_assembly`) — a `gate`/`wall` with no void neighbor (e.g. a locked door gating a windowless side room, never meant to connect elsewhere) simply isn't picked as a room-to-room connector; it still works as an ordinary in-room obstacle. **Consequence:** rooms saved under the old rule (gate/wall anywhere on FLOOR) now have zero valid entry-exits until their gate/wall objects are dragged onto a proper wall cell in the editor — `move_object` re-validates through the same check, so the palette of valid cells is discoverable by just trying to drop it somewhere.
- `core/world/assembly.py`: `PlacedRoom` wraps a `Dungeon` with a floor index and a global grid offset. `generate_assembly(room_names, room_count)` starts from the first room (in `room_names` order) with both a `spawn` and a valid `gate`/`wall` entry-exit, then repeatedly draws another room at random from `room_names` (repeats allowed) and attaches it at one of the growing assembly's unconnected entry-exits — aligned so the two entry-exit objects share the same global cell. The candidate's exit is only ever chosen from objects matching the anchor exit's own type (a `gate` merges with a `gate`, a `wall` with a `wall`, never mixed) so both halves of one physical doorway share the same sprite/animation. If the new room's tiles would conflict with an already-placed room on the same floor (anything except two rooms' auto-generated wall halos meeting, or the entry-exit cell itself — both expected, not conflicts), it goes on floor +1 instead (or -1 if that's also occupied), always relative to the floor of the room it's connecting from.
- Cross-room link inheritance: rather than copying the anchor exit's local `links` verbatim (meaningless once the two ends live in different rooms' object lists), `generate_assembly` finds any `button` in the anchor room whose `links` reference the anchor exit and appends a global, floor-qualified `assembly_links` entry (`{"floor", "x", "y"}`) pointing at the candidate's merged door.
- `save_assembly(assembly, name)`/`load_assembly(name)` persist to `assets/donjons/<name>.json` as one combined file: each room is stored fully (`SaveManager.to_json()` per room, plus its floor/offset) rather than just a reference to its source room file, since generation mutates objects (link inheritance, `portal_level` below) that a fresh reload from `assets/rooms/` would lose. `Creator._apply_generation` calls `save_assembly` right after generating (via `next_new_donjon_name()`), and `RoomPanelUI`'s "Charger" lists donjons alongside rooms so a saved one can be reloaded.
- `Creator.open_donjon(name)` loads a saved assembly and `Creator.run()` renders it (`DungeonAssembly.render`, `active_floor=0`) in place of the normal single-room edit view whenever `self.last_assembly` is set — painting/object tools are suspended while previewing (they act on `self.dungeon`, not what's on screen); `ESC` closes the preview before it falls through to the menu.
- **Collision is scoped to the player's current floor, on purpose.** Two `PlacedRoom`s on different floors routinely share a bounding box (they're often the same source room reused), so `DungeonAssembly.locate_room(global_x, global_y, floor, prefer_room=None)` only ever searches `rooms_on_floor(floor)` — never other floors — checking FLOOR ownership first and falling back to "any non-empty cell" (a WALL halo) only if nothing on that floor claims FLOOR there. Searching every floor at once (the original design) let the player "phase" through a wall solid on their own floor whenever an unrelated room on another floor happened to have FLOOR at that same global cell. `is_global_cell_walkable`/`is_rect_walkable`/`check_button_trigger` all take the same explicit `floor` and mirror the single-`Dungeon` equivalents through it.
- **Crossing floors is an explicit, data-driven portal, not a side effect of collision.** Whenever a connection actually lands on a different floor, `generate_assembly` stamps a `"portal_level"` field directly onto *both* halves of the doorway (the anchor's exit object and the candidate's exit object) — the half-integer midpoint between the two floors it bridges (e.g. `0.5` between floors 0 and 1, `1.5` between 1 and 2), the same value on both sides since it's the same physical staircase either way. It's additive, just like `variant`/`links`/`open` — no separate room-level list, so it round-trips through `SaveManager`'s already-generic `objects` list for free. `DungeonAssembly.find_portal(room, global_x, global_y)` reads the object at that cell and derives the actual target floor relative to whichever side you're asking from: `target = 2 * portal_level - room.floor`. Reaching a portal cell at all already implies the current floor's own collision allowed it (e.g. a button-opened gate), so no separate "is it open" check is needed before crossing. Same-floor attachments don't get a `portal_level` — ordinary same-floor room-crossing already works via `locate_room`.
- `Explorator._update_current_room()` resolves same-floor room-crossing via `locate_room`, then checks `find_portal` on the result to flip `self.current_placed_room` (and therefore floor) when the player steps onto a portal cell. `_is_walkable`/button-triggering pass `self.current_placed_room.floor` explicitly into the assembly API above.
- **Rendering** (`DungeonAssembly.render(screen, camera, active_floor, player_world_pos=None, ...)`): the active floor draws directly onto `screen`; floors below are drawn onto an offscreen per-pixel-alpha surface and alpha-multiplied down to `BELOW_FLOOR_ALPHA` (45/255, a faint tint) before compositing; floors above are alpha-multiplied to `ABOVE_FLOOR_ALPHA` (235/255, a near-opaque "ceiling") and then punched with a circular hole (`BLEND_RGBA_MULT` against a mask surface) of radius `VISION_RADIUS_TILES` (2.5 tiles, in screen pixels scaled by `camera.zoom`) centered on `player_world_pos` — a continuous pixel position, not a grid cell — so the ceiling fades away exactly where the player's field of view reaches it, revealing the active floor underneath. `player_world_pos=None` (Creator's static preview, which has no player) renders floors above fully opaque. `skip_active_floor_foreground` + `render_active_floor_foreground()` let a caller that draws its own player sprite (`Explorator`) interleave the player between the active floor's tiles and its foreground objects (e.g. an L/R torch), same z-order as the single-room case. This superseded the old single-hidden-grid-cell approach, so `hide_cells` was removed from `WorldRenderer`/`Dungeon.render()` entirely (no other callers).
- `Menu`'s Explorer picker lists donjons alongside rooms (mirroring `RoomPanelUI`'s `(kind, name)` tuple pattern) via `GameManager.pending_room`.

**First non-player entities: wandering animal NPCs — done, editor placement and live Explorator behavior:**
- Four animal object types (`chicken`, `cow`, `pig`, `sheep`) were added to `OBJECT_TYPES`/`OBJECT_LIST`, each backed by `assets/characters/Animals/<Name>.png` — a 64x64 sheet, 2x2 grid of 32px frames (row 0 idle, row 1 move) — flagged `"animal": True`, from which `object_manager.ANIMAL_TYPES` is derived (`tuple(name for name, cfg in OBJECT_TYPES.items() if cfg.get("animal"))`) instead of a separately-maintained list. They use the plain `"floor"` placement rule, same as `vase`, so they drop/drag/save through the exact same `ObjectPalette`/`ObjectTool`/`ObjectManager.add_object`/`SaveManager` path as every other object — no new plumbing was needed there.
- `ObjectPalette` (`core/editor/ui.py`) used to lay its icons out in a single row sized for the original 6 object types; with 10 now, `load_icons()` wraps into a `COLUMNS = 5` grid and computes `self.height` from the resulting row count, and `Creator` positions `GeneratorPanelUI` below it (`y=object_palette.y + object_palette.height + 20`) instead of a hardcoded offset, so the two panels never overlap regardless of how many object types exist.
- `load_object_frames()` (the static-icon loader shared by the palette and `WorldRenderer`) grew a `config.get("frame_size", ...)` lookup instead of a hardcoded 16px (24px for `spawn`) — an animal's `"frame_size": 32` combined with its `"frames": 2` means it reads exactly the idle row, so a placed animal shows as a static idle-frame icon in both the palette and the editor grid, identical in spirit to how `vase`/`torch` render.
- **Live behavior is a separate loader and a separate entity, deliberately not folded into `ObjectManager`.** `load_animal_frames()` (`object_manager.py`) reads the *full* 2x2 sheet into `{"idle": [...], "move": [...]}`, and `core.world.entities.Animal` — a new class alongside `Player` — owns per-frame wandering behavior: a random timer alternates `idle`/`move`, entering `move` picks a random direction (any angle, not just 4-directional) and a random duration, and position updates are collision-checked per-axis exactly like `Player.update` (movement on an axis is simply skipped if the resulting hitbox isn't walkable — no bounce/redirect). `AnimalManager` (also in `entities.py`) owns the *list* of live `Animal`s for one `Dungeon`, spawned from its placed animal objects via `spawn()` — mirroring `ObjectManager`'s "dungeon-owned component" shape, but for per-frame NPC behavior instead of static placement rules, and kept as its own list rather than mixed into `ObjectManager.objects` so a wandering `Animal`'s live position never gets confused with its origin object's fixed grid cell (the placed object itself never moves — that's what actually round-trips through `room.json`).
- `Dungeon` owns an `AnimalManager` (`self.animal_manager`) alongside its existing `ObjectManager`/`WorldRenderer`/`SaveManager`, and `Dungeon.update(dt, player_hitbox=None)` now advances it too (`object_manager.update(dt)` + `animal_manager.update(dt, player_hitbox=...)`). `Dungeon.render()` draws `self.animal_manager` after the normal tile/object pass (no y-sorting against the player — out of scope for this first pass). **Spawning is opt-in, not automatic**, via `Dungeon.spawn_animals()`: it's *not* called from `rebuild()`/`paint_cell()` (which would reset every animal's wandering state on every single paint stroke) and *not* called by `Creator` at all (whose static preview only ever wants the frame-0 icon, matching every other object type) — only `Explorator` calls it, right after loading a room (`open_room`, `load_spawn_room`) or each room of a loaded assembly (`open_donjon`). Because `DungeonAssembly.update(dt, player_hitbox=None, player_floor=None)` was changed to call `room.dungeon.update(dt, player_hitbox=...)` (previously it called `room.dungeon.object_manager.update(dt)` directly, and passed no player info at all), and rendering already threads every room's own `Dungeon.render()` through an `_OffsetCamera` per floor (`_render_floor`/`_render_floor_tinted`/`_render_floor_masked`), animals in a procedurally-assembled dungeon get the exact same per-floor update/tint/mask treatment as tiles and objects for free — no assembly-specific animal code was needed. `player_hitbox` is only ever forwarded to the room on `player_floor`; every other room gets `None`, so an animal on a floor the player isn't physically standing on never collides with them (mirrors `locate_room`'s per-floor scoping).
- `Explorator`'s module-level `HIDDEN_OBJECT_TYPES = {"spawn", *ANIMAL_TYPES}` replaces the old `{"spawn"}` literal at all four of its `hide_object_types=` render call sites, so a placed animal's static object icon never double-renders alongside its live `Animal` sprite during exploration.

**Animal collision/animation polish — done:**
- **Fixed a real 1px wall-clip bug** (reproduced with a 20000-frame stress test: an animal's hitbox ended up overlapping a WALL cell in ~15% of frames before the fix, 0 after). Root cause: the original `Animal.update` mutated a `pygame.Rect` in place (`hitbox.x += movement.x`) to build the candidate hitbox it tested, then applied the raw float `movement.x` straight to `self.position.x` on success — but assigning a float to a `Rect` field *rounds*, while `get_hitbox()` (called fresh every other frame) *truncates* (`int(...)`) from the live float position. Those two roundings of the same quantity can disagree by a pixel, so a move could validate against a rect that was up to 1px more conservative than the hitbox the animal actually settled into. Fixed by adding `Animal._hitbox_at(x, y)` — the one formula both `get_hitbox()` and collision-testing now share — and testing candidate positions by computing `self._hitbox_at(candidate_x, self.position.y)` directly from the prospective float position instead of mutating an existing Rect, so the tested hitbox and the one the animal actually ends up with are always identical.
- **Animal-vs-animal and animal-vs-player collision**, previously nonexistent (animals and the player could freely overlap). `AnimalManager._is_free(rect, moving_animal, player_hitbox)` checks, in order: `Dungeon.is_rect_walkable` (walls/closed gates, cheapest/most likely to reject), every *other* live animal's current hitbox via `rect.colliderect(...)`, then the player's hitbox if supplied. This is the `is_walkable` callback `AnimalManager.update` now hands each `Animal.update` (one small lambda closure per animal per frame, capturing that animal so it never collides with itself). Symmetrically, `Explorator._is_walkable` (used for the player's own movement) was extended to also reject any candidate rect overlapping a live animal in the player's current room, so the player can't walk through an animal either — both directions use plain `Rect.colliderect`, i.e. exact pixel-rect overlap, not a coarser cell-level check.
- **Animation flip direction fixed**: the animal sheets face left by default (opposite of `Player`'s sheets, which face right), so `Animal._enter_state("move")` now sets `self.flip = self.direction.x > 0` (flip when heading right) instead of the original `direction.x < 0` (which had it backwards — an animal walking right displayed its left-facing idle/move frames un-flipped).

**Assembly-mode collision offset fix, and Y-sorted entity rendering — done:**
- **Real bug: animal-vs-player collision compared local and global coordinates directly in a multi-room assembly.** An `Animal`'s `.position` (and therefore `get_hitbox()`) is always local to its own room's `Dungeon` — it's built via that room's own `grid_to_world`, with no `PlacedRoom.offset_x`/`offset_y` baked in (the offset only ever gets applied at render time, via `_OffsetCamera`). The player's hitbox, by contrast, is global (`Explorator`/`Player.position` always carry the room offset already summed in). `DungeonAssembly.update` was handing that global `player_hitbox` straight to each room's `AnimalManager` unmodified, so for any room not sitting at offset `(0, 0)` the animal-vs-player overlap check was comparing two rects in different coordinate spaces — reproduced with a large-offset stress test (offset 100 tiles: the "block" never registered at all). Fixed by having `DungeonAssembly.update` shift `player_hitbox` back into each room's local frame (`player_hitbox.move(-room.offset_x * tile_size, -room.offset_y * tile_size)`) before passing it down, mirroring how `is_global_cell_walkable` already converts global to local before delegating to a room's own `ObjectManager`. Animal-vs-animal collision was never affected (both sides always compared within the same room's local coordinates already).
- **Y-sorted rendering of live entities** (player + animals): previously `Dungeon.render()` always drew every animal in one unconditional pass *before* `Explorator` drew the player afterward, so the player was always in front regardless of actual on-screen depth. `Dungeon.render(..., skip_animals=False)` and `DungeonAssembly.render(..., skip_active_floor_animals=False)` (which threads it through `_render_floor`) let a caller opt the *active* floor's animals out of that automatic pass; floors below/tinted and above/masked always draw their animals normally (no player there to sort against, and they're dimmed background regardless). `Explorator.render()` now does its own combined pass afterward: single-room branch sorts `dungeon.animal_manager.animals + [player]` by `.position.y` (their shared feet-anchor, the same quantity `get_hitbox()` anchors to) and draws in that order, so whichever entity sits lower on screen (greater y, closer to camera in a top-down view) draws in front; the assembly branch does the same via the new `DungeonAssembly.render_active_floor_entities(screen, camera, active_floor, player)`, gathering animals across every room on the active floor (converting each to a comparable global y — `animal.position.y + room.offset_y * tile_size` — purely for the sort key; actual drawing still goes through that room's own `_OffsetCamera`) plus the player, in one sorted pass. Both call sites replace what used to be a bare `player.draw(...)` call, now sandwiched between `render(..., skip_..._animals=True)` and the existing foreground-object pass (`render_foreground`/`render_active_floor_foreground`), so the z-order is: floor tiles/objects → sorted animals+player → foreground objects (L/R torches), same slot the player alone used to occupy.

**Player: remaining action animations and inputs — done:**
- Four more animation sheets were already listed in `Player.ANIMATIONS` (`attack`, `interact`, `jump`, `run`) and `Player.cut_sheet()` already derived each row's frame count from that specific sheet's own pixel width (`columns = sheet.get_width() // FRAME_WIDTH`), not a hardcoded constant — so no loader changes were needed to support `attack.png` (6 frames/row), `interact.png` (4), `jump.png` (5), and `run.png` (6) each having a different frame count. `jump.png` is also short a row (110px tall = 4 rows, not the full 5 `DIRECTIONS` — it has no `"back"` frames), which `cut_sheet`'s existing `if row >= len(DIRECTIONS): break` guard tolerated for *loading*, but `update()`/`draw()` still indexed `self.sprites[animation][direction]` directly and would `KeyError` the moment the player faced `"back"` while jumping. Fixed with `Player._frames_for(animation, direction)`, now used by both, which falls back to `"front"` and then to whatever direction the sheet *does* have.
- **One-shot action animations**: `attack`/`interact`/`jump` (`Player.ONE_SHOT_ANIMATIONS`) play through once and hand control back, unlike the looping `idle`/`walk`/`run`. `Player.play_action(name)` starts one (no-op if another action is already mid-playback, or if that sheet failed to load) by setting `self.action = name` alongside `self.animation`; `Player.update()` clears `self.action` back to `None` the moment that animation's frame counter would otherwise wrap past its last frame, instead of looping it. `Explorator` only assigns `self.player.animation = "run"/"walk"/"idle"` from movement state when `self.player.action is None`, so a triggered action animation isn't stomped by the very next frame's movement-driven assignment, and resumes normally once the action completes.
- **Inputs**: `Explorator.run()`'s event loop now also handles `MOUSEBUTTONDOWN` (button 1 → `play_action("attack")`, button 3 → `play_action("interact")`) and `KEYDOWN` `K_SPACE` (→ `play_action("jump")`) — one-shot triggers, unlike movement's continuous `pygame.key.get_pressed()` polling. `SHIFT` (either key) is polled every frame in `Explorator.update()` alongside `Z`/`Q`/`S`/`D`: holding it while moving swaps `MOVE_SPEED` (180px/s) for the new `RUN_SPEED` (260px/s) and picks the `"run"` animation over `"walk"`.

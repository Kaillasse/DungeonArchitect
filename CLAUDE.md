# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Dungeon Architect — a top-down, tile-based roguelike editor/game built with pygame. Players will explore procedurally-composed dungeons and unlock tiles/monsters/traps/entities for a fully customizable, destructible home base between runs. See `DA.txt` (French) for the full design pitch and current priority list.

The grid uses 16x16px source art; each world grid cell renders that art at 2x, so a logical cell is 32x32px (see `core.data.ressources.WORLD_SCALE`). Rooms are composed of these cells and saved as JSON under `assets/rooms/`.

## Commands

- Run the app: `python main.py` (opens the main menu, `GameState.MENU`).
- Dependencies: `pygame==2.6.1`, declared in `requirements.txt`. **That file is UTF-16LE encoded** (not UTF-8) — `pip install -r requirements.txt` may fail to parse depending on pip version; if so just `pip install pygame==2.6.1` directly. A `.venv` already exists in the repo root.
- Headless smoke-test of the editor: set `DUNGEONARCHITECT_HEADLESS=1` before running — `GameManager` skips the menu and starts straight in `GameState.CREATOR`, and `Creator.run()` saves the current room and exits immediately instead of opening the pygame window/event loop.
- There is no test suite, linter, or build config in the repo.

## In-app controls

- Menu: `UP`/`DOWN` (or `Z`/`S`) to move the selection, `ENTER` or mouse click to confirm, `ESC` quits. Choosing "Editeur de salle" or "Explorer" opens a room-picker (see Architecture) before actually entering that state — "+ Nouvelle salle" (Creator only) starts a fresh untitled room.
- Editor (Creator): left-click an empty floor cell to paint, left-click-drag an already-placed object's body to move it, left-click-drag a linkable object's indicator dot (top-right corner of its tile — `button`/`gate`/`wall`) onto another one's dot to link them, drag object icons from the palette onto the grid to place new ones, right-click erase, mouse-wheel zoom, `TAB` switch to exploration, `ESC` back to menu. The Sauvegarder/Charger/Supprimer panel (top of screen) replaces the old F1-F4 console shortcuts entirely — each button opens a scrollable room list to pick a target and a "Valider" button to confirm.
- Exploration (Explorator): French AZERTY movement (`Z`/`Q`/`S`/`D`, not WASD), mouse-wheel zoom, `TAB` back to editor, `ESC` back to menu. Walking onto a linked `button` opens whatever `gate`/`wall` it's linked to.

## Architecture

`main.py` builds the pygame `screen` and hands it to `GameManager`, whose `run()` loop dispatches on `core.engine.gamestate.GameState` (`MENU` / `CREATOR` / `EXPLORATION`). Each state object owns **its own inner pygame event loop** (`Menu.run()`, `Creator.run()`, `Explorator.run()`) rather than there being one shared frame loop — switching state means setting `self.state` and breaking out of the current inner `while` loop, which returns control to `GameManager.run()` to dispatch into the next state's loop.

Package layout (`core/`):
- `engine/` — state machine plumbing: `GameManager` (also owns `pending_room`, set by `Menu`'s room-picker before switching to `CREATOR`/`EXPLORATION`; `run()` applies it via `creator.open_room()`/`explorator.open_room()` right before dispatching into that state's loop), `GameState`, `Camera` (world↔screen coordinate/zoom transform), `RoomManager` (thin wrapper around `Dungeon.save_to_json`/`load_from_json`/deleting a room file, plus `scan()`/`next_new_room_name()` — holds no "current room" state itself, that's each caller's concern; no console I/O, unlike its previous `input()`-driven incarnation).
- `editor/` — the room editor (`Creator`, the `CREATOR` state): `ui.py` has `ToolPaletteUI`, `ObjectPalette` (the draggable object-type icon tray, reuses `object_manager.load_object_frames`), `RoomPanelUI` (Sauvegarder/Charger/Supprimer buttons, each opening a `core.ui.RoomBrowser` + "Valider" button — `handle_event()` returns `(mode, room_name)` once confirmed, letting `Creator` do the actual save/load/delete); `tools.py` has `ObjectTool` (drag state for placing an object from the palette onto the grid); `autotile.py` is the tile-logic core (see below).
- `world/` — the dungeon data model: `dungeon.py` (`Dungeon` owns `width`/`height`/`logical_grid`/`sprite_grid` directly and orchestrates an `ObjectManager` + `WorldRenderer` + `SaveManager`; grid↔world coordinate conversion; `is_rect_walkable`/`update(dt)` delegate to `ObjectManager` — it draws nothing, saves nothing, and doesn't manage objects itself), `object_manager.py` (`ObjectManager(dungeon)` — takes the dungeon it belongs to; the `OBJECT_TYPES`/`OBJECT_LIST` registry of placeable object metadata — asset path, placement surface, footprint size in cells, frame count, and the gameplay flags `walkable`/`blocks_movement`/`blocks_until_open`/`linkable`; `get_object_at()` is footprint-aware (matches any cell a multi-cell object like `wall` covers, not just its origin); `is_cell_walkable()` is the single source of truth for whether a cell can be walked into, and `is_foreground_object()` the one for whether an object draws in front of / is walkable-despite-being-on-a-wall (currently: an L/R torch only, not the plain straight one); `check_button_trigger()`/`update(dt)` drive button→gate/wall activation and its frame-by-frame animation (holds on the last frame once reached — doesn't loop); `load_object_frames()` slices a sprite sheet, shared by the editor palette and the renderer), `entities.py` (`Player` — sprite-sheet animation keyed by direction, mirrors left-facing sprites from the right-facing frames, hitbox anchored at the feet; stub `NPC`/`Enemies` classes not yet wired up).
- `data/` — `ressources.py` (asset/tileset path resolution, tile metadata JSON loading, the `ROOMS_DIRECTORY` constant, `TILE_SIZE`/`WORLD_SCALE`, `list_rooms()`/`next_new_room_name()`), `save_manager.py` (`SaveManager` — stateless `save(dungeon, room_name)` / `load(dungeon, room_name)`, converts a `Dungeon` to/from its JSON room file).
- `rendering/` — `world_renderer.py` (`WorldRenderer.render(screen, dungeon, camera, spawn_preview=None, hide_object_types=None, show_link_indicators=False, skip_foreground_objects=False)`: draws the tile grid with a `(tile_index, zoom)` surface cache, placed objects sized from `OBJECT_TYPES[type]["size"]` (in grid cells, not raw sprite pixels) and at their current `obj["frame"]`, debug grid lines, the spawn-preview marker, and (only when `show_link_indicators=True`, which only `Creator` passes) each linkable object's indicator dot and any persisted links. `render_foreground_objects()` draws only objects `ObjectManager.is_foreground_object()` flags — `Explorator` calls it after drawing the player so a foreground object (an L/R torch) overlaps the player instead of the other way around; `Creator` never calls it since it draws no player sprite, so it just renders everything in one `render()` pass. Holds no world state itself — only pygame surface caches).
- `menu.py`, `explorator.py`, `ui.py` (top-level, not in a subpackage) — `Menu` (the `MENU` state: title screen with Editeur/Explorer/Parametres/Quitter, routes to `CREATOR`/`EXPLORATION` — but first through a room-picker mode reusing `core.ui.RoomBrowser`, setting `game_manager.pending_room` and `.state` once "Valider" is clicked; `ESC` from either gameplay state now returns here instead of quitting — only the menu itself quits the program), `Explorator` (the `EXPLORATION` state: player movement/collision, camera follow; `open_room(name)` loads a specific room and spawns the player in it, used both by the menu's room-picker and its own startup auto-discovery fallback `load_spawn_room()`), `ui.py` (`BorderManager`, the shared 9-slice panel renderer used by both the editor UI and `Menu`; `RoomBrowser`, a scrollable/slider-scrollable selectable room-name list — purely a list-selector, callers decide what confirming a selection means; used by both `Menu`'s room-picker and `RoomPanelUI`).

Autotiling (`core/editor/autotile.py`), the core "logical grid" algorithm: cells are `EMPTY`/`FLOOR`/`WALL` ints. `build_walls()` does a two-pass pass over the grid — strip existing `WALL` cells back to `EMPTY`, then surround every `FLOOR` cell's empty neighbors (8-directional) with `WALL`. `resolve_sprite_grid()` then computes a 4-directional (`up`/`right`/`down`/`left`) neighbor bitmask string like `"0212"` per non-empty cell and looks up `(category, bitmask)` in `AUTOTILE_LOOKUP`, which is built at import time from `assets/tiles/tile_categories.json`, to pick the concrete sprite index.

## Roadmap

**Object placement rules — done:**
- `ObjectManager.add_object` now reads `OBJECT_TYPES[type]["placement"]` (`"floor"` or `"wall"`) instead of hardcoding `FLOOR` for every type — this also fixed a real bug where `torch` (wall-only) could never actually be placed.
- `Dungeon.paint_cell` calls `object_manager.prune_invalid()` after every edit, which drops any placed object whose cell no longer matches its placement rule — so erasing a floor destroys the `gate`/`wall`/`button`/`vase`/`spawn` sitting on it, and erasing the floor that generated a wall segment destroys any `torch` mounted there too.
- `spawn` is excluded from rendering during exploration: `WorldRenderer.render(..., hide_object_types=...)`, with `Explorator` passing `{"spawn"}`. `Creator` passes nothing, so it still shows in the editor.
- `torch` gets an L/R wall-mount variant chosen at placement time (`ObjectManager._wall_variant`): floor immediately to the wall's left → `R`, floor immediately to the wall's right → `L`, no adjacent floor on either side (the common straight-wall case) → the plain front-facing sprite. Stored as an optional `"variant"` key on the object dict (additive — old saves without it still load).

**Button/gate/wall linking — done, editor and runtime:**
- Any `button`/`gate`/`wall` (`OBJECT_TYPES[type]["linkable"]`) shows a small indicator dot at `Dungeon.object_indicator_position(obj)` (top-right corner of its cell) whenever `Creator` renders — `Explorator` never passes `show_link_indicators`, so links/indicators are invisible during exploration, per spec.
- Dragging from one indicator to another calls `ObjectManager.link()`, which records the connection symmetrically on both objects as an additive `"links"` list of `{"x", "y"}` targets (same additive-JSON-field approach as `torch`'s `"variant"` — old saves without it still load fine).
- `ObjectManager.move_object()` lets any placed object (not just linkable ones) be dragged to a new cell in `Creator` — it re-validates the placement rule at the destination, recomputes a torch's L/R variant if it moved, and retargets any other object's `links` that pointed at its old cell. `prune_invalid()` also drops links left dangling when the object they pointed at gets erased.
- At runtime: `Explorator.update()` calls `ObjectManager.check_button_trigger(grid_x, grid_y)` every frame using the player's hitbox (`hitbox.centerx`, `hitbox.bottom - 1` — not raw `player.position`, which sits exactly on the cell's bottom boundary and would floor-divide into the row below). Stepping onto an unactivated `button` sets `obj["activated"] = True` and opens (`obj["open"] = True`) every `gate`/`wall` it's linked to; it's a one-shot latch, not a toggle. `ObjectManager.update(dt)` (called from `Dungeon.update`, which `Explorator` calls every frame) advances `obj["frame"]` for any activated/open object at a fixed rate and **holds on the last frame** once reached rather than looping.
- Walkability is `ObjectManager.is_cell_walkable(x, y)`, not a raw `logical_grid` check: `button` is always walkable; `torch` is walkable **only** when it has an L/R variant (`ObjectManager.is_foreground_object`) — an L/R torch is mounted on a side wall the player needs to walk past, so it's also drawn in front of the player instead of blocking; the plain straight torch (mounted on a back wall, no adjacent floor to either side) stays a normal blocking wall decoration, since making it walkable would mean walking straight through a wall. `gate`/`wall` block until their `"open"` flag is set. `vase` always blocks (`"blocks_movement"`). `Dungeon.is_rect_walkable` (used for player-movement collision) delegates to `is_cell_walkable` per hitbox corner instead of checking `WALL` directly.
- `get_object_at(x, y)` is footprint-aware: it matches any cell within `OBJECT_TYPES[type]["size"]` of an object's origin, not just the origin itself. This is what makes a 2-wide `wall` object correctly block (and later open) *both* of its cells, not just the one it was placed on — it also means clicking the second cell of a wide object in `Creator` lets you grab it to move, same as clicking its origin cell.
- These are all additive object-dict fields (`activated`, `open`, `frame`, `anim_timer`), so a saved room can reload with its buttons/gates already mid- or fully-triggered.

**Procedural room-to-room generation** (further out, not started): detect a room's entry/exit points (via its `gate`/`wall` objects), then propose or procedurally place adjacent rooms whose own entry/exit objects match type-for-type. Overlap at a junction should be resolved by shifting the new room ±1 floor/layer (multi-floor dungeons, not just single rooms) rather than by moving tiles within a floor. When floors are stacked, the player standing below an occupied floor above them should be able to see through to it (a rendering concern — `WorldRenderer` currently renders exactly one `Dungeon`'s grid, with no concept of multiple stacked floors at all).

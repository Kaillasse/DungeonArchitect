## Project

Dungeon Architect — a top-down, tile-based roguelike editor/game built with pygame. Players explore procedurally-composed dungeons and unlock tiles/monsters/traps/entities for a fully customizable, destructible home base between runs. See `DA.txt` (French) for the original design pitch — superseded by this file's own "État actuel"/"Objectifs" sections below and by `done.txt`'s full history.

The grid uses 16x16px source art; each world grid cell renders that art at 2x, so a logical cell is 32x32px (see `core.data.ressources.WORLD_SCALE`). Single rooms are saved as JSON under `assets/rooms/`; procedurally-assembled multi-room dungeons under `assets/donjons/`.

## État actuel — fonctionnalités du programme

- **Éditeur (Creator)** : peinture Sol/Mur autotile, panneaux dockables/déplaçables/redimensionnables (Outils, Sauvegarder/Charger, Cartes, Générateur), objets liés bouton→porte, générateur procédural de donjons multi-room/multi-étage avec portails entre étages.
- **Exploration** : mouvement/collision AZERTY, combat (joueur, squelettes), animaux/ennemis errants, inventaire (slots principaux + monnaie + grille générale), chute dans le vide, franchissement d'étage via portails.
- **Génération procédurale** : assemblage multi-room/multi-étage à partir d'un pool de rooms choisi par le joueur, rôles d'E/S (connecteur / entrée de donjon / sortie de donjon).
- **Progression** : XP/niveaux, profils joueurs persistants (`assets/profiles/`).
- **Home** : room "home" auto-créée par joueur, bascule par zoom entre Exploration et Creator dessus, le programme démarre directement dans le home.
- **Multijoueur** : co-op local (clavier 2/manette, vrai split-screen avec fusion d'écran automatique quand les joueurs partagent une room), réseau LAN complet (serveur autoritaire, prédiction/réconciliation côté client, chat + commandes, hébergement/rejoindre une partie depuis le home). **Connexion par adresse IP hors LAN : actuellement non fonctionnelle** — seul le mode LAN (broadcast UDP) est opérationnel ; connu, volontairement non prioritaire pour l'instant (voir "Mis de côté" ci-dessous).
- **Système de Cartes** : modèle de données pontant `OBJECT_TYPES`/`ITEM_DEFINITIONS`/les rooms elles-mêmes, panneau collection (liste + grille agrandie, survol, focus), consommation/remboursement exacts à la pose/effacement (y compris halo autotile et objets cassés en cascade), glisser-déposer direct depuis la collection (vers la grille, le Générateur, ou la Forge), rooms devenues cartes (miniature top-down, remboursement à la suppression, manifest/contenu-du-pack affiché), Générateur redimensionnable en mode grille de cartes. La palette d'objets de l'éditeur est entièrement pilotée par la collection de cartes (le blocage par niveau de progression existe toujours en parallèle mais n'est plus le mécanisme actif).
  - **Registre unifié** : `OBJECT_TYPES` (built-in + custom, mécaniques de jeu éditables sur N'IMPORTE QUEL type via la Forge/`MechanicsPanelUI`, override persisté sans toucher au Python source) et `ITEM_DEFINITIONS` (idem, plus un vrai registre d'item custom `register_item`/`update_item`) partagent le même modèle. `card_type` stocké explicitement (`tile_decor`/`tile_special`/`item`/`mob`/`room`/`pnj`). Capacités (`capabilities`, ex. lançable/explosif de la dynamite) et effets (`Card.effects`, ex. "Soin" via `Player.heal()`, déclenché par le slot interact) sont des vocabulaires génériques réutilisables, pas câblés en dur — visibles de façon cohérente partout (carte composée de la collection, panneau détail, Forge).
  - **La Forge (`MechanicsPanelUI`)** a une seule zone de prévisualisation animée (160x160), unifiée pour tous les types de carte : mob (onglets sur ses états — `ENEMY_ANIMATIONS` pour un ennemi, idle/move pour un animal), objet décoratif/spécial multi-frame (boucle automatique, sans onglet), PNJ (sprite tagué par rôle `wander_actions`, glisser-cliquer sur le sprite pour tourner parmi les 8 directions), item (icône statique, une seule frame). Vue dédiée par type au-delà de l'aperçu : objet (mécaniques éditables), item/mob/PNJ (capacités/effets éditables — ex. lançable/explosif, "Soin"), mob **enemy** en plus (PV/vitesse/aggro/portée + loot monnaie/objet éditables via des Steppers, `active_attack_frames` jamais exposé pour ne pas casser l'anim de combat). Toujours non éditable : réassignation des rôles PNJ (quelle action taguée correspond à idle/move/etc.) — reste le rôle de l'éditeur de sprite séparé ; stats d'animal (n'en a pas).
- **Éditeur de sprite (`SpriteEditorPanelUI`)** : 4 modes — "Tuile" (recadre une région d'un PNG en carte placable), "Pack" (grille de tuiles individuelles extraites vers un pack autotile/entité), "Bitmap" (tag bitmask/variante ou action/direction/ordre sur un pack déjà extrait), et **"Pixel"** — seul mode qui touche vraiment aux pixels : pinceau carré (roue teinte/saturation + curseur de luminosité + taille), pipette, sélection rectangulaire libre au pixel près, copier/couper/coller (Ctrl+C/X/V), annuler (Ctrl+Z, pile de 20), sur n'importe quel PNG du dépôt ou une toile vierge nouvellement créée (écrite sous `assets/tiles/custom_sprites/`). "Enregistrer" écrase le fichier source en place. Ne crédite jamais de carte lui-même — produit/modifie le PNG qu'un des 3 autres modes recadre/tag ensuite.

## Objectifs

### Court terme

- **En cours** : nouvelles tuiles + refonte de l'architecture de récupération/gestion des tiles et sprites, pour simplifier l'ajout de nouvelles tuiles et préparer les futurs outils d'éditeur de sprite.

### Moyen terme (v0.05 — "créateur de donjon procédural, rogue like multijoueur")

- **Tileset extérieur** (herbe, terrain de home/overworld) — prérequis pour un home qui ressemble vraiment à un extérieur, et plus tard pour la carte MMORPG v1.
- **Tuiles spéciales** : mob spawner continu (fait apparaître des ennemis pendant l'exploration, pas seulement au chargement de la room), "graveur de CD" (concept encore à préciser avec l'utilisateur).
- **PNJ réels** avec interaction/dialogue (pas de simples `Animal`/`Enemy` qui errent) : Le Collectionneur (échange des cartes), L'Artiste (fournit de quoi créer — à préciser), Le Forgeron (rôle à préciser), Le Chat/Gepeto (PNJ d'intro/tuto, candidat pour un placement par défaut dans un home fraîchement créé).
- **Outil de visualisation/édition de sprite** + création de nouveau sprite, utilisable pour n'importe quelle Carte (tuile/mob/item) — dépend directement de la refonte tile/sprite en cours. La prévisualisation animée existe déjà pour tous les types dans la Forge (voir ci-dessus), et l'édition/création de pixels existe désormais dans l'éditeur de sprite (mode "Pixel", voir ci-dessus). Ce qui reste : éditer/créer un sprite directement depuis la Forge elle-même (pas seulement depuis l'éditeur de sprite séparé), et des outils de dessin moins rudimentaires (brosse ronde, alpha, remplissage, collage flottant plutôt qu'immédiat).
- **Système de Cartes, ce qui reste hors scope** : effets au-delà de "Soin" (dégât, buff temporaire — ce dernier nécessite un système de minuteur/modificateur par joueur qui n'existe pas du tout), déclenchement d'effet par ramassage/placement (aujourd'hui uniquement via le slot interact), édition de carte room au-delà de la repeinte en Creator, cartes de monnaie, tuile de base (sol/mur/bitmask/variantes — sous-système autotile séparé, pas encore ramené dans le registre carte unifié), UI de création d'item en jeu (existe seulement comme fonction Python, pas de panneau dédié).
- **Destructibilité de l'environnement** en exploration (certains monstres/objets/effets détruisent le décor).
- **Assembleur avancé** (piste séparée, différée par l'utilisateur) : tags/dossiers de rooms, slider min/max de rooms par tag, taille de donjon plafonnée par le niveau de progression du joueur.
- **Multijoueur Phase 7** : delta-compression des snapshots réseau. Jamais vérifié avec 4 clients réseau simultanés (seulement 2 en LAN) — à revalider une fois le contenu réseau-synchronisé (cartes/PNJ/spawners) en place.

### Long terme (v1 — "ouverture en MMORPG")

- Chaque joueur a son home et sa collection de cartes, entièrement personnalisables.
- Les homes sont disposés côte à côte pour former une carte jouable en ligne partagée : jusqu'à 4 voisins par joueur, avec permissions d'accès gérées par le joueur lui-même.
- Implique un monde persistant partagé (le `GameServer` actuel est éphémère, en mémoire, lié à une session d'hébergement précise), une vraie identité de compte (au-delà du nom de joueur local actuel), et un modèle de placement spatial des homes (grille de parcelles + voisinage + permissions). À ne pas commencer avant que v0.05 — en particulier le système de Cartes, les PNJ et le home — soit stable.

### Mis de côté (décision explicite du 2026-08-11, pas un simple report)

- **Serveur de rendez-vous/matchmaking + tunnel** pour jouer hors LAN : l'utilisateur préfère éviter à la fois un hébergeur tiers et l'auto-hébergement d'un service relais qui reviendrait au même problème de service fragile à maintenir soi-même. L'adresse manuelle (IP/hostname résolvable, ex. DDNS) et la découverte LAN restent la solution supportée pour se connecter — indépendamment du bug de connexion IP mentionné plus haut, qui reste à corriger séparément le jour où ce chemin redevient prioritaire.


## Commands

- Run the app: `python main.py` (opens the main menu, `GameState.MENU`).
- Dependencies: `pygame==2.6.1`, declared in `requirements.txt`. **That file is UTF-16LE encoded** (not UTF-8) — `pip install -r requirements.txt` may fail to parse depending on pip version; if so just `pip install pygame==2.6.1` directly. A `.venv` already exists in the repo root.
- Headless smoke-test of the editor: set `DUNGEONARCHITECT_HEADLESS=1` before running — `GameManager` skips the menu and starts straight in `GameState.CREATOR`, and `Creator.run()` saves the current room and exits immediately instead of opening the pygame window/event loop.
- There is no test suite, linter, or build config in the repo.

## In-app controls

- Menu: `UP`/`DOWN` (or `Z`/`S`) to move the selection, `ENTER` or mouse click to confirm, `ESC` quits. Choosing "Editeur de salle" or "Explorer" opens a room-picker (see Architecture) before actually entering that state — "+ Nouvelle salle" (Creator only) starts a fresh untitled room.
- Editor (Creator): left-click an empty floor cell to paint, left-click-drag an already-placed object's body to move it, left-click-drag a linkable object's indicator dot (top-right corner of its tile — `button`/`gate`/`wall`) onto another one's dot to link them, drag object icons from the palette onto the grid to place new ones, right-click erase, mouse-wheel zoom, `TAB` switch to exploration, `ESC` back to menu (or, while previewing a generated dungeon, closes the preview first — see below). The Sauvegarder/Charger/Supprimer panel (top of screen) replaces the old F1-F4 console shortcuts entirely — "Charger" lists both rooms (`[Salle] name`) and saved dungeons (`[Donjon] name`) together. Below it (left column, under the tool/object palettes) is the generator panel: a room pool (checkbox-style multi-select, defaults to every saved room) and a room count (+/- stepper); "Generer" runs the procedural assembler, saves the result to `assets/donjons/`, and immediately shows it — while previewing, painting/object tools are suspended (they act on the normal single-room `Dungeon`, which isn't what's on screen).
- Exploration (Explorator): French AZERTY movement (`Z`/`Q`/`S`/`D`, not WASD), hold `SHIFT` to run (faster movement + `run` animation instead of `walk`), left-click to attack, right-click to interact, `SPACE` to jump (one-shot animations — see done.txt), mouse-wheel zoom, `TAB` back to editor, `ESC` back to menu. Walking onto a linked `button` opens whatever `gate`/`wall` it's linked to.

## Architecture

`main.py` builds the pygame `screen` and hands it to `GameManager`, whose `run()` loop dispatches on `core.engine.gamestate.GameState` (`MENU` / `CREATOR` / `EXPLORATION`). Each state object owns **its own inner pygame event loop** (`Menu.run()`, `Creator.run()`, `Explorator.run()`) rather than there being one shared frame loop — switching state means setting `self.state` and breaking out of the current inner `while` loop, which returns control to `GameManager.run()` to dispatch into the next state's loop.

Package layout (`core/`):
- `engine/` — state machine plumbing: `GameManager` (also owns `pending_room`, set by `Menu`'s room-picker before switching to `CREATOR`/`EXPLORATION`; `run()` applies it via `creator.open_room()`/`explorator.open_room()` right before dispatching into that state's loop), `GameState`, `Camera` (world↔screen coordinate/zoom transform), `RoomManager` (thin wrapper around `Dungeon.save_to_json`/deleting a room file, plus `scan()`/`next_new_room_name()` — holds no "current room" state itself, that's each caller's concern; no console I/O, unlike its previous `input()`-driven incarnation), `input.py` (`InputState` — a per-frame input snapshot for one player, plus `read_local_keyboard_input(settings)`, a pure function fully separate from applying one; see done.txt's multiplayer-refactor phase history).
- `editor/` — the room editor (`Creator`, the `CREATOR` state): `ui/` is a subpackage, one file per panel (split from a single 2988-line `ui.py` once that became unwieldy — `ui/__init__.py` re-exports every panel class so `from core.editor.ui import X` still works unchanged) — `tool_palette.py` has `ToolPaletteUI`, `ObjectPalette` (the draggable object-type icon tray, reuses `object_manager.load_object_frames`); `room_panel.py` has `RoomPanelUI` (Sauvegarder/Charger/Supprimer buttons, each opening a `core.ui.widgets.RoomBrowser` + "Valider" button — `handle_event()` returns `(mode, selection)` once confirmed; for "load", `selection` is a `(kind, name)` tuple (`"room"` or `"donjon"`), since "Charger" lists both; for "save"/"delete" it's a plain room name); `generator_panel.py` has `GeneratorPanelUI` (a multi-select `RoomBrowser` for the room pool, a `core.ui.widgets.Stepper` for the room count, and a "Generer" button — `handle_event()` returns `(room_names, room_count)` once confirmed, letting `Creator` call `generate_assembly()`, save it, and preview it); `chest_panel.py` has `ChestPanelUI` (a `Stepper` per currency/item loot row for a placed chest); `card_renderer.py`/`card_panel.py` have `CardRenderer`/`CardPanelUI` (the Cartes collection panel); `role_panel.py`, `autotile_theme_panel.py`, `sprite_editor.py` have `RolePanelUI`, `AutotileThemePanelUI`, `SpriteEditorPanelUI` (see done.txt for what each does — `sprite_editor.py` alone is still ~1600 lines, the in-app sprite/autotile-pack editor). `tools.py` has `ObjectTool` (drag state for placing an object from the palette onto the grid); `autotile.py` is the tile-logic core (see below).
- `world/` — the dungeon data model: `dungeon.py` (`Dungeon` owns `width`/`height`/`logical_grid`/`sprite_grid` directly and orchestrates an `ObjectManager` + `WorldRenderer` + `SaveManager`; grid↔world coordinate conversion; `is_rect_walkable`/`update(dt)` delegate to `ObjectManager` — it draws nothing, saves nothing, and doesn't manage objects itself), `object_manager.py` (`ObjectManager(dungeon)` — takes the dungeon it belongs to; the `OBJECT_TYPES`/`OBJECT_LIST` registry of placeable object metadata — asset path, placement surface, footprint size in cells, frame count, and the gameplay flags `walkable`/`blocks_movement`/`blocks_until_open`/`linkable`; `get_object_at()` is footprint-aware (matches any cell a multi-cell object like `wall` covers, not just its origin); `is_cell_walkable()` is the single source of truth for whether a cell can be walked into, and `is_foreground_object()` the one for whether an object draws in front of / is walkable-despite-being-on-a-wall (currently: an L/R torch only, not the plain straight one); `check_button_trigger()`/`update(dt)` drive button→gate/wall activation and its frame-by-frame animation (holds on the last frame once reached — doesn't loop); `load_object_frames()` slices a sprite sheet, shared by the editor palette and the renderer), `assembly.py` (the procedural room-to-room assembler — see done.txt), `entities.py` (`Player` — sprite-sheet animation keyed by direction, mirrors left-facing sprites from the right-facing frames, hitbox anchored at the feet; `Animal`/`AnimalManager` — the first live NPCs, see done.txt; `Enemy`/`EnemyManager` — skeleton1/skeleton2, see done.txt for aggro/attack behavior).
- `data/` — `ressources.py` (asset/tileset path resolution, tile metadata JSON loading, the `ROOMS_DIRECTORY`/`DONJONS_DIRECTORY` constants, `TILE_SIZE`/`WORLD_SCALE`, `list_rooms()`/`next_new_room_name()`/`list_donjons()`/`next_new_donjon_name()`), `save_manager.py` (`SaveManager` — stateless `save(dungeon, room_name)` / `load(dungeon, room_name)`, converts a `Dungeon` to/from its JSON room file; `apply_json(dungeon, payload)` factors out the payload-application half of `load()` so the assembly loader can reuse it per-room without a room-name-based file lookup).
- `rendering/` — `world_renderer.py` (`WorldRenderer.render(screen, dungeon, camera, spawn_preview=None, hide_object_types=None, show_link_indicators=False, skip_foreground_objects=False, hide_cells=None)`: draws the tile grid with a `(tile_index, zoom)` surface cache, placed objects sized from `OBJECT_TYPES[type]["size"]` (in grid cells, not raw sprite pixels) and at their current `obj["frame"]`, debug grid lines, the spawn-preview marker, and (only when `show_link_indicators=True`, which only `Creator` passes) each linkable object's indicator dot and any persisted links. `hide_cells` (a set of local (x, y)) skips specific cells entirely (tile and object) — used by `DungeonAssembly.render()` for the see-through hole. `render_foreground_objects()` draws only objects `ObjectManager.is_foreground_object()` flags — `Explorator` calls it after drawing the player so a foreground object (an L/R torch) overlaps the player instead of the other way around; `Creator` never calls it since it draws no player sprite, so it just renders everything in one `render()` pass. Holds no world state itself — only pygame surface caches).
- `ui/` — the state-agnostic shared UI layer, plus `Menu` (which is built almost entirely out of it and owns no world/simulation state of its own, unlike Creator/Explorator, so it lives here rather than in its own subpackage): `widgets.py` has `BorderManager` (the shared 9-slice panel renderer used by editor UI, `Menu`, and `InventoryPanel` alike — a singleton, first-initialized by whichever of those constructs it first), `RoomBrowser` (a scrollable/slider-scrollable selectable room-name list, with an optional `multi_select` mode (checkbox-style, toggles into `selected_set`) — purely a list-selector, callers decide what confirming a selection means; used by `Menu`'s room-picker, `RoomPanelUI`, and `GeneratorPanelUI`), `BorderPicker` (Settings > Bordure's clickable tile-sheet grid), `Stepper` (a "-  N  +" row — rects + min/max-clamped value changes on click; used by `editor/ui.py`'s `GeneratorPanelUI`/`ChestPanelUI`, previously each hand-rolled). `menu.py` has `Menu` (the `MENU` state: title screen with Editeur/Explorer/Parametres/Quitter, routes to `CREATOR`/`EXPLORATION` — but first through a room-picker mode reusing `RoomBrowser`, setting `game_manager.pending_room` and `.state` once "Valider" is clicked; `ESC` from either gameplay state now returns here instead of quitting — only the menu itself quits the program).
- `exploration/` — the `EXPLORATION` state, mirroring `editor/`'s "one game state = one subpackage, its own UI bundled alongside it" shape: `explorator.py` has `Explorator` (`self.players: dict[int, PlayerSession]` — see done.txt's multiplayer-refactor phase history for why this replaced a single `self.player`/`self.inventory` — drives movement/collision/combat/camera-follow; `open_room(name)` loads a specific room and (re)spawns every current session's player in it, used both by the menu's room-picker and its own startup auto-discovery fallback `load_spawn_room()`; also has `run_networked(client)`, `apply_network_snapshot(payload)`, `add_network_session`/`remove_session`/`adopt_local_player_id` — the Phase 3 client/server entry points, see done.txt); `player_session.py` has `PlayerSession` (bundles one player's `Player`, `Inventory`/`InventoryPanel`, per-frame `InputState`, and UI/audio state that's per-player, not per-world-session — `input_source_kind` includes `"network"` since Phase 3); `inventory_ui.py` has `InventoryPanel` (the "E" overlay, Explorator-only — not in `core/ui/widgets.py`, which is reserved for widgets actually shared across game states, same separation as `editor/ui.py` being Creator-only).
- `network/` — the multiplayer transport layer (see Roadmap in done.txt for the phase-by-phase history): `protocol.py` (newline-delimited JSON message framing — `encode`/`encode_dict`/`decode` — plus `build_snapshot(explorator, tick, terrain_versions)`, the one place that knows the wire schema for a full world snapshot), `server.py` (`GameServer` — headless, owns one `Explorator`, fixed-tick loop), `client.py` (`NetworkClient` — thin socket-to-queue pump, no simulation).

Autotiling (`core/editor/autotile.py`), the core "logical grid" algorithm: cells are `EMPTY`/`FLOOR`/`WALL` ints. `build_walls()` does a two-pass pass over the grid — strip existing `WALL` cells back to `EMPTY`, then surround every `FLOOR` cell's empty neighbors (8-directional) with `WALL`. `resolve_sprite_grid()` then computes a 4-directional (`up`/`right`/`down`/`left`) neighbor bitmask string like `"0212"` per non-empty cell and looks up `(category, bitmask)` in `AUTOTILE_LOOKUP`, which is built at import time from `assets/tiles/tile_categories.json`, to pick the concrete sprite index.
